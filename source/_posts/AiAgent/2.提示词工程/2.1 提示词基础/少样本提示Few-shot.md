# 少样本提示（Few-shot Prompting）

给模型一两个“标准答案”示例，比写十行规则描述都管用。


## 一、什么是少样本提示

少样本提示（Few-shot Prompting）是指在提示词中提供少量 **输入→期望输出** 的示例，让模型通过模式模仿来完成新任务，而不需要重新训练。


基本结构：

```text
[系统/角色设定]

示例 1:
输入：...
输出：...

示例 2:
输入：...
输出：...

现在请处理以下输入：
输入：...
输出：
```


与零样本（Zero-shot）的对比：

| 方式 | 特点 | 适用场景 |
| -- | -- | -- |
| 零样本 | 只给指令，不给示例 | 任务简单、模型基础能力足够 |
| 少样本 | 给 1~5 个示例 | 格式严格、领域术语特殊、逻辑需要示范 |

在 Agent 开发中，工具描述、输出格式约定、状态分类 等场景几乎离不开少样本提示。


## 二、为什么少样本提示有效

从模型行为角度看，大语言模型本质是一个 **模式补全器**。当你在提示词中给出示例，模型会：

1. **提取模式**：自动识别输入与输出之间的映射关系（如格式、语调、逻辑）。

2. **激活相关参数**：将内部的知识分布向示例所代表的“任务类型”倾斜。

3. **减少不确定性**：对于模糊指令，示例消除了“到底是哪种意思”的歧义。

对于全栈开发者可以这样类比：少样本示例就像给一个动态类型语言写 **接口定义 + 单元测试用例**，虽然没有编译检查，但足以约束行为边界。


## 三、示例设计的原则

### 1. 覆盖度优先，而非数量优先

示例要覆盖任务的主要变化类型，而不是随便给几个。

❌ 不好的选择（同质化）：

```text
示例1：把“你好”翻译成“Hello”
示例2：把“谢谢”翻译成“Thank you”
示例3：把“再见”翻译成“Goodbye”
```
→ 模型只会单词翻译，遇到句子就乱。

✅ 好的选择（边界覆盖）：

```text
示例1：单词 → “你好” → “Hello”
示例2：短语 → “非常感谢” → “Thank you very much”
示例3：完整句子 → “请问洗手间在哪？” → “Where is the restroom?”
示例4：带否定 → “我不喜欢这个” → “I don't like this”
```
→ 覆盖了长度、结构、否定等典型变体。

### 2. 示例要“干净”，不含无关信息

每个示例的输入输出应严格对应任务，不要夹杂解释、评价或多于的空格换行。

❌ 脏示例：

```text
输入：用户说“我登录不了”
输出：这应该归类为“账号问题”，摘要写成“登录失败”，我说得没错吧？
```

✅ 干净示例：

```text
输入：用户说“我登录不了”
输出：{"category":"account","summary":"登录失败"}
```

### 3. 输出格式严格一致

如果输出是 JSON，所有示例的输出都必须是合法的 JSON，且字段顺序、缩进风格相同。模型对格式的模仿是“像素级”的。

## 四、示例数量：多少才够

经验值（针对主流模型如 GPT-4o、Claude 3.5）：

| 示例数量 | 适用任务 |
| -- | -- | 
| 0（零样本） | 简单任务，模型已充分见过 |
| 1~2 | 格式输出要求严格，但任务逻辑简单 |
| 3~5 | 需要多分类判断、有领域术语 |
| 6~10 | 复杂推理链、需同时控制格式与逻辑 |
| >10 | 极少使用，会挤占上下文、引入噪声 |

**Agent 工具调用中的特殊考量**：
工具描述 + 参数 schema 本质上已充当了“一个示例”。此时再额外补充 1~2 个带完整输入输出的示例，就能显著提升调用准确率。

## 五、示例的摆放位置

**推荐顺序（从上到下）**：

```text
[System]  角色、任务总述、硬性约束
[示例块]  示例1、示例2……
[User]    当前需要处理的真实输入
```

**为什么这样排**：

- System 中的约束是“基础框架”
- 示例紧接着细化“怎么做”
- 真实的 User 输入放在最后，让模型在生成时，上下文最近的内容是示例 → 模仿动力最强

避免把示例放在 System 区。System 区的内容模型倾向于作为“背景知识”而非“直接模仿模板”，放在 User/Assistant 交替对话中效果更好。

在 Chat API 中，可以这样构造消息数组：

```python
messages = [
    {"role": "system", "content": system_prompt},
    {"role": "user", "content": "示例输入1"},
    {"role": "assistant", "content": "示例输出1"},
    {"role": "user", "content": "示例输入2"},
    {"role": "assistant", "content": "示例输出2"},
    {"role": "user", "content": real_user_input}
]
```
通过 user/assistant 交替，模型会把示例当作“之前完成过的对话”，从而更自然地继承格式与逻辑。

## 六、Agent 场景中的典型应用

### 6.1 工具选择与参数提取
```text
示例1：
用户：帮我查下北京明天的天气
你需要调用：get_weather({city: "Beijing"})

示例2：
用户：上海后天会下雨吗
你需要调用：get_weather({city: "Shanghai"})

现在：
用户：深圳今天温度多少
你需要调用：
```

### 6.2 多分类与路由
```text
将用户问题分类为：ACCOUNT, BILLING, TECH_SUPPORT, OTHER

示例1：
用户：我忘记密码了
分类：ACCOUNT

示例2：
用户：为什么我的信用卡被扣了两次费？
分类：BILLING

示例3：
用户：你们的APP一直闪退
分类：TECH_SUPPORT

现在：
用户：我要注销账号
分类：
```

### 6.3 Agent 多步推理（ReAct 轨迹）
```text
你需要用“思考→行动→观察”的格式解决用户问题。

示例：
用户：北京今天天气如何？如果下雨就提醒我带伞。
思考：需要先查天气。
行动：get_weather(city="Beijing")
观察：多云，降水概率10%
思考：不会下雨，无需提醒带伞。
回答：今天北京多云，没有雨，不用带伞。

现在：
用户：深圳明天最高温度多少？
```

## 七、常见问题与调优方法

| 现象 | 可能原因 | 解决 |
| -- | -- | -- |
| 模型忽略格式，输出自由文本 | 示例格式不一致或示例放在了 system 区 | 用 user/assistant 交替放置，并确保所有示例格式完全一致 |
| 输出内容刻板照抄示例 | 示例过少且同质化严重 | 增加覆盖不同情况的高质量示例，并在 system 提示中强调“按示例风格，而非复制内容” |
| 示例越多效果反而变差 | 示例之间存在矛盾，或上下文窗口被撑满 | 精简示例至 3~5 个，删除低质量样例 |
| 对未见过的输入表现差 | 示例未覆盖边界情况 | 分析失败 case，针对性地补充 1~2 个新示例 |
| Token 消耗过高 | 示例太长 | 将示例压缩为最小必要形式，或使用 GPT-4o-mini 等低成本模型做路由 |

## 八、与 Agent 提示词模板的关系
在 2.4 节“Agent中的提示词模板”中你会看到，一个 ReAct 风格的 Agent 提示词模板本质上就是：

```text
[角色] + [工具清单] + [Few-shot 交互示例] + [当前上下文]
```
少样本示例直接决定了 Agent 在运行时如何组织“Thought → Action → Observation”的步骤。可以说，Agent 行为的稳定性，一半靠工具描述，一半靠 Few-shot 示例的质量。

你现在需要的是刻意练习：拿起一个你全栈工作中常见的分类或格式转换任务，用 3 个示例去替代一段冗长的指令，对比两者的效果差异。这件事做一次，比看十页理论都有用。
