## 角色指令与输出格式

把提示词想象成给一个超级实习生写需求文档——他能力极强，但如果你说不清楚，他就瞎猜，猜错了锅在你。

## 一、核心认知

提示词的四个要素，缺一不可：

｜ 要素 ｜ 全栈类比 ｜ 作用 ｜
｜ -- ｜ -- ｜ -- ｜
｜ 角色 ｜ 定义这个微服务的职责边界 ｜ 框定行为模式 ｜
｜ 指令 ｜ 接口的请求参数与处理逻辑 ｜ 告诉模型做什么、怎么做 ｜
｜ 上下文 ｜ 请求头里的 metadata + body 里的业务数据 ｜ 提供执行所需背景信息 ｜
｜ 输出格式 ｜ 定义接口的 response schema ｜ 约束返回结构 ｜


## 二、角色设定

为什么要设角色？ 模型在海量数据上学了各种“人格”，你不指定，它就随机选一个。指定角色等于告诉模型：从你的知识空间里，调取这个特定身份对应的语言风格、知识范围、行为模式。


**角色设定的三层结构**：

```text
你是一个 [身份/角色]，专注于 [领域/任务]，你的风格是 [风格约束]。
```

**错误示范**：

```text
你是一个助手。
```

**正确示范**：

```text
你是一个资深后端工程师，专注于 Python FastAPI 微服务架构。
你的回复风格：
- 代码优先，先给可运行的代码，再解释原理
- 命名遵循 PEP 8 规范
- 看到性能问题时主动指出并给出优化方案
- 不确定的技术点会明确说明"我推测……"
```

**写角色的核心原则**：

- 用**肯定句**描述应该做什么（不要用否定句描述不该做什么，模型对否定句的理解不稳定）
- 越具体越好，"资深 Python 后端工程师" 好过 "程序员"
- 风格约束可以列点，模型对列表式约束的执行力更强


**常见角色模板速查**：

｜ 场景 ｜ 角色定义要点｜
｜ -- ｜ -- ｜
｜ 代码生成 ｜ 语言、框架、版本、代码风格、注释习惯 ｜
｜ 文档撰写 ｜ 受众是谁、正式/口语化、是否需要引用来源 ｜
｜ 数据提取 ｜ 从什么格式中提取、提取哪些字段、空值处理规则 ｜
｜ Agent 工具调用 ｜ 可用工具有哪些、调用时机判断标准、错误处理策略 ｜

## 三、指令结构化

指令是你给模型的任务描述。结构化的意思是：把模糊的自然语言任务，拆解成清晰的步骤和约束。

**指令结构化的三要素**：

```text
[任务目标]：一句话说清楚要完成什么
[执行步骤]：分步描述具体怎么做
[约束条件]：有哪些边界和限制
```

对比：不结构化 vs 结构化

❌ 不结构化：

```text
帮我总结一下客户反馈的问题，分类整理一下发给我。
```
（模型会随机决定分类标准、总结粒度、输出格式，结果每次都不一样）

✅ 结构化：

```text
[任务目标] 对客户反馈邮件进行分类摘要

[执行步骤]
1. 逐封阅读以下邮件内容
2. 识别每封邮件的核心问题类型（产品缺陷 / 使用咨询 / 投诉建议）
3. 同类问题合并，提取共性问题描述
4. 统计每个类别的问题数量

[约束条件]
- 只关注产品功能相关的问题，忽略物流、价格等无关话题
- 每个问题一句话概括，不超过30字
- 如果某封邮件问题模糊无法归类，标记为"待人工处理"并附原文
- 先输出分类统计，再输出详细列表
```

指令写好的小技巧：

- 步骤用数字编号，模型按顺序执行的成功率远高于段落式描述
- 约束条件放在最后，心理学上的"近因效应"，模型对最后出现的约束更敏感
- 用 Markdown 的 #、-、1. 来分块，模型在训练时见过大量 Markdown 文档，结构识别能力强
- 给出"不知道怎么办"的兜底规则，防止模型瞎编

## 四、上下文

上下文是模型执行指令所需的背景信息。在 Agent 开发中，上下文通常来自三个来源：

### 1. 对话历史（短期记忆）

这是你之前在 1.2.2 学过的多轮对话管理。要点：

- system prompt 放角色和长期约束
- user/assistant 交替放对话历史
- 历史太长需要截断时，优先保留最近的对话

```python
messages = [
    {"role": "system", "content": system_prompt},      # 角色 + 固定约束
    {"role": "user", "content": "第一个问题"},          # 历史
    {"role": "assistant", "content": "第一个回答"},     # 历史
    {"role": "user", "content": "当前问题"}             # 最新用户输入
]
```
### 2. 外部检索数据（RAG 上下文）

从向量库搜出来的文档片段，注入方式：

```text
请根据以下参考信息回答问题：

[参考文档1]
内容……
来源：xxx

[参考文档2]  
内容……
来源：xxx

[问题]
用户的实际问题……

[回答要求]
如果参考信息不足以回答问题，请明确说明"当前信息不足"，并建议用户补充哪些信息。
```

关键点：**一定要求模型在不确认时说出来**，RAG 最大的坑就是检索结果不相关时模型强行编答案。

### 3. 系统运行时数据

Agent 当前状态、工具返回结果、用户偏好等：

```text
[当前时间]：2026-07-24 14:30
[用户身份]：高级会员，权限等级 3
[可用工具]：get_weather, search_knowledge_base, create_ticket
[当前状态]：已完成天气查询，等待用户下一步指令
```

## 五、输出格式约束

输出格式约束是提示词工程最重要的组件之一，也是你后端全栈最大的优势——你对 JSON Schema 和结构化数据的理解可以直接平移到这里。

三种层次，由松到严：

### 层次 1：自然语言描述格式

```text
用以下格式回复：
**问题类型**：[产品缺陷 / 使用咨询 / 投诉建议]
**处理建议**：……
**需要升级**：是 / 否
```

适用于：非关键场景、人看为主、格式一致性要求不高。

### 层次 2：强制 JSON 输出（非结构化输出的模型）

```text
请严格按以下 JSON 格式回复，不要输出任何其他内容：
{
  "category": "bug" | "question" | "complaint",
  "summary": "一句话总结",
  "needs_escalation": true | false,
  "suggested_action": "处理建议"
}
```
注意：你得在代码里 try...catch JSON 解析，因为模型可能多输出一个 ```json 标记或者最后一个 } 后面多了文字。

### 层次 3：Function Calling / Structured Output（最稳）

这是 OpenAI 的结构化输出模式，底层强制约束 token 生成，不会出现格式错误：

```python
from openai import OpenAI
client = OpenAI()

response = client.chat.completions.create(
    model="gpt-4o-mini",
    messages=[{"role": "user", "content": "用户反馈登录按钮点不了"}],
    response_format={
        "type": "json_schema",
        "json_schema": {
            "name": "feedback_classifier",
            "strict": True,
            "schema": {
                "type": "object",
                "properties": {
                    "category": {
                        "type": "string",
                        "enum": ["bug", "question", "complaint"]
                    },
                    "summary": {"type": "string"},
                    "needs_escalation": {"type": "boolean"},
                    "suggested_action": {"type": "string"}
                },
                "required": ["category", "summary", "needs_escalation", "suggested_action"],
                "additionalProperties": False
            }
        }
    }
)

result = response.choices[0].message.content  # 这就是合法的 JSON 字符串
```
输出格式设计的核心原则：

- 能穷举的字段用 enum，不要用自然语言描述，防止模型自己造分类
- 标注 required 字段，明确哪些必须有值
- 给每个字段写 description，这是字段级别的"微指令"
- additionalProperties: false，防止模型往 JSON 里加戏

## 六、一个综合案例
把角色、指令、上下文、输出格式串起来，写一个"客户反馈分类器"的完整 System Prompt：

```python
system_prompt = """# 角色
你是一个客户反馈分类专家，专精于 SaaS 产品的用户反馈分析。
你的分析风格：客观、精确、不猜测。不确定的分类宁可归类为"其他"也不硬套。

# 当前上下文
[当前时间]：2026-07-24
[产品模块]：用户认证系统、支付模块、数据看板
[优先级规则]：涉及支付的问题优先级 +1，涉及登录无法使用的问题优先级 +1

# 指令
分析用户的反馈信息，完成以下任务：
1. 识别反馈涉及的产品模块
2. 判断反馈的问题类型
3. 评估紧急程度（1-5，5 最紧急）
4. 生成一句话行动建议

# 约束
- 如果反馈内容模糊无法判断模块，归类为"其他"
- 如果涉及多个模块，选最主要的那个
- 紧急程度评估只看功能影响，不看用户情绪
- 不要添加任何分析之外的评论

# 输出格式
严格输出 JSON，不包含任何其他文字：
{
  "module": "auth" | "payment" | "dashboard" | "other",
  "type": "bug" | "feature_request" | "question" | "complaint",
  "urgency": 1-5,
  "action": "一句话建议"
}
"""
```
