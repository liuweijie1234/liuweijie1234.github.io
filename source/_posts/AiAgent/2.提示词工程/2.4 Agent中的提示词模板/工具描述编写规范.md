## 2.4 Agent 提示词模板：工具描述编写规范

工具描述（tool description）是 Agent 提示词里**性价比最高**的一段文字——模型能不能选对工具、传对参数，七成取决于它写得好不好。

### 一个工具描述的组成

以 Function Calling / JSON 工具定义为例，每个工具通常有三要素：

```json
{
  "name": "search_weather",
  "description": "查询指定城市的实时天气，返回温度、天气状况与降水概率。当用户问到天气、出行建议、温度时调用。",
  "parameters": {
    "type": "object",
    "properties": {
      "city": {"type": "string", "description": "城市名，如 '北京'、'Shanghai'"},
      "unit": {"type": "string", "enum": ["celsius", "fahrenheit"], "description": "温度单位，默认 celsius"}
    },
    "required": ["city"]
  }
}
```

### 编写规范（实战经验）

1. **description 写「什么时候用 + 返回什么」**：不要只写「查询天气」，要写清触发场景和输出，模型才能正确路由。
2. **参数 description 写「取值含义与示例」**：`city` 写成「城市名，如北京」比光秃秃的 `string` 准确得多。
3. **能用 enum 就别自由文本**：`unit` 用枚举，模型几乎不会传错。
4. **明确 required**：缺必填参数会直接报错，提前声明省一轮重试。
5. **避免工具名歧义**：两个工具名相似（如 `get_user` / `get_users`）极易让模型选错，命名要唯一且自解释。
6. **工具数量克制**：一次性塞 30 个工具，模型选择准确率直线下降。按需动态加载（只给当前任务相关的工具）。
7. **工具描述统一语气**：都用「执行 XX 动作，返回 XX」句式，模型更易形成稳定预期。

### 反例 vs 正例

反例：

```json
{
  "name": "tool1",
  "description": "处理数据",
  "parameters": {"type": "object", "properties": {"a": {"type": "string"}}}
}
```

正例：

```json
{
  "name": "query_order",
  "description": "根据订单号查询订单状态与物流信息。当用户提供订单号并询问『我的快递到哪了』时调用。",
  "parameters": {
    "type": "object",
    "properties": {
      "order_id": {"type": "string", "description": "订单号，形如 'NO20240101001'"}
    },
    "required": ["order_id"]
  }
}
```

### 进阶：工具描述的「元信息」

- 给工具标 `category`（搜索/计算/业务），运行时按任务动态挑选；
- 在描述里标注「是否需要人类确认」（高危操作如退款、发邮件）；
- 工具描述也要进版本管理，改了描述要回归测试选择准确率。
