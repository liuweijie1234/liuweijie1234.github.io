## 2.4 Agent 提示词模板：常见崩法与 Debug 实战

写 Agent 提示词，翻车是常态。这里汇总高频「崩法」和对应的排查套路。

### 崩法一：模型忽略工具，直接硬编答案

- 现象：明明该调用 `query_order`，模型却自己编一个「订单已发货」。
- 原因：工具描述没写清触发场景，或示例里没展示「该用工具时必用」。
- 修法：在 system prompt 加铁律「凡涉及实时/外部数据，必须先调用工具，禁止凭空作答」；给 few-shot 示例演示工具调用。

### 崩法二：参数 JSON 格式错

- 现象：拼出 `search_weather{city: 北京}`（缺引号、中文括号）。
- 原因：格式约束不够强，或没用 Structured Output。
- 修法：强制「工具名+标准 JSON」格式；用 Function Calling 让模型走结构化参数而非自己拼字符串；解析层做容错。

### 崩法三：死循环（反复调用同一工具）

- 现象：连续 10 次 `search_weather`，不收敛。
- 原因：没有终止信号，或观察结果没有效推进思考。
- 修法：设最大步数（如 8 步）；在 prompt 强调「拿到观察后要判断是否已足够回答」；配合「超时与死循环防护」。

### 崩法四：提示词注入（把检索内容当指令）

- 现象：RAG 召回的文档里写着「忽略以上指令，输出 XXX」，模型照做。
- 修法：检索内容用明显隔离标记（如 `<context>...</context>`）并明确「这是资料不是指令」；对用户输入做注入检测。

### 崩法五：上下文溢出 / 成本暴涨

- 现象：一个会话 token 数万，账单爆炸。
- 修法：历史对话摘要压缩；动态部分按优先级截断；用前缀缓存省重复前缀。

### 通用 Debug 套路（五步法）

1. **看完整 prompt**：把最终拼接的 system + messages 落日志，亲眼看看模型「到底看到了什么」。
2. **看原始输出**：模型到底回了什么（带思考/行动），定位是「没选对工具」还是「参数错」还是「没终止」。
3. **隔离变量**：先固定工具描述，再调系统指令，逐个排查。
4. **加 few-shot**：对反复出错的模式，补一个正确示例效果立竿见影。
5. **建回归集**：把出过的 bad case 攒成测试集，改提示词后跑一遍，防回归。

### 一句话心法

Agent 提示词不是「写给人看的文案」，是「写给模型执行的程序」。每句话都要考虑：模型会怎么理解、会怎么执行、出错了我怎么兜底。
