## 3.6 RAG 常见踩坑排查

RAG 上线后最常被问「为什么答不对」，按症状快速定位：

### 症状一：检索不到 / 召回空空

- 分块太大或被切断，语义被稀释 → 调小 chunk、加重叠、改语义切分。
- Embedding 模型选错（中英文不匹配）→ 中文换 BGE/M3E。
- 元数据过滤 `where` 条件写错，全被过滤掉 → 先去掉过滤验证。
- 向量库没真正写入（upsert 失败/集合名错）→ 查库里到底有没有数据。

### 症状二：答非所问 / 用了错误资料

- 最相关块排在后面被截断 → 加 **Reranker** 精排（最常见根因）。
- top_k 太大引入噪声 → 收紧到 3~5。
- 检索和生成语言/领域不一致 → 统一语料与提示词。

### 症状三：幻觉（一本正经编答案）

- 提示词没约束「只依据资料」→ 加「资料不足就说不知道」。
- 召回质量差，模型被迫编 → 先治检索再治生成。
- 混合检索缺失，专有名词搜不到 → 加 BM25 关键词召回。

### 症状四：幻觉来源定位难（不可溯源）

- 没做引用标注 → 答案带 `[1][2]` 编号，前端可跳转原文。
- 没记 source 元数据 → 预处理阶段补齐来源字段。

### 症状五：成本高 / 慢

- 每次都全量重算 → 用缓存（相同 query 直接取历史结果）。
- 注入过多无关上下文 → 检索后压缩、只留相关句。
- Reranker 用得太早 → 只在候选集上用，别在海量上用。

### 排查通用流程

1. 看召回：把检索返回的 chunks 打印出来，人工判断「对不对、排没排前」；
2. 看生成：固定同一批 chunks，换提示词看是否改善；
3. 二分定位：检索差先治检索，检索好却答错再治生成。
