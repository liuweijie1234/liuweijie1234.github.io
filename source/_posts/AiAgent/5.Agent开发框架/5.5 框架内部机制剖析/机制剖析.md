## 5.5 框架内部机制剖析

理解框架「底层在干什么」，能帮你少踩坑、做优化。两个最值得懂的机制：提示词自动拼装、Token 缓存。

### 1. 提示词自动拼装原理

无论是 LangChain 还是 LangGraph，最终喂给模型的，都是**框架在运行时帮你拼出来的一段 messages**：

```
[系统提示词]  ← 框架默认角色 + 你写的 instructions
[记忆/历史]   ← Memory 模块从存储里取出的对话
[工具描述]   ← 你注册的 Tool 被序列化成 JSON Schema 注入
[检索上下文]  ← RAG 检索到的 chunks（仅 RAG 场景）
[用户输入]    ← 当前这条消息
```

框架做的事：

1. 把各组件（PromptTemplate、Memory、Tool、Retriever）的输出按固定顺序拼接；
2. 对工具做 `function` 声明注入；
3. 处理多轮：把 assistant 的工具调用和 tool 的返回作为 `tool` 角色消息回填；
4. 把最终 messages 发给模型，再把模型响应按角色解析回各组件。

**代价**：抽象层会生成比你手写更啰嗦的 prompt（塞了很多默认说明），且不易完全掌控。所以复杂场景常「框架搭骨架 + 自定义关键 prompt 块」。

### 2. Token 缓存与加速

LLM 推理时，prompt 的前缀（system + 长指令 + 工具定义）往往**每次请求都一模一样**。推理服务可以缓存这部分的计算结果（KV Cache）：

- **前缀缓存（Prefix Cache）**：相同前缀只算一次，后续请求直接复用，显著降低首 token 延迟和成本。
- 实践启示：
  - 把**不变的系统指令、工具定义**放在 prompt 最前面，让缓存命中；
  - 把**易变内容（用户问题、检索结果）**放最后，避免击穿缓存；
  - 部分推理平台（如 Claude、Gemini、vLLM）支持显式 cache_control 标记。

```python
# 伪代码：让不变的指令进缓存
messages = [
    {"role": "system", "content": STATIC_INSTRUCTION, "cache_control": "ephemeral"},
    {"role": "user", "content": dynamic_question},  # 易变，不缓存
]
```

### 3. 其他机制（了解）

- **流式解析**：框架边收 SSE 边把 tool_call 拼完整，再触发执行；
- **重试与降级**：模型调用失败时的退避重试，由框架或你自己实现；
- **可观测埋点**：LangSmith 等把每次拼装后的完整 prompt、token、延迟记录下来。

### 经验

- 卡顿/成本高，先查「是不是每次都重传了大段不变前缀」→ 用前缀缓存；
- 行为诡异，先 `print` 出框架最终拼的 messages，往往真相大白；
- 框架是加速器不是黑盒，懂原理才能驾驭。
