## 6.3 信息共享与冲突解决

多 Agent 协作的难点不在「各自干活」，而在「怎么互通、怎么不打架」。

### 1. 共享记忆黑板（Blackboard）

最经典的共享机制：维护一块**公共黑板（Blackboard）**，所有 Agent 读写同一份中间状态。

```
Agent-A 写: {结论: "方案X更优", 依据: [...]}
Agent-B 读黑板 → 基于A的结论继续补充
```

实现上就是一块共享存储（内存字典 / Redis），对应 Agent 的「工作记忆 / 长期记忆」。好处是解耦（Agent 间不直接耦合），坏处是要防并发写冲突。

### 2. 消息路由与广播

- **点对点**：Manager 把任务精准派给某个 Worker；
- **广播**：一条消息发给所有 Agent（如「任务目标更新了」）；
- **发布订阅**：Agent 订阅自己关心的主题（如「价格」频道），只收相关消息。

框架层（AutoGen 的 GroupChat、LangGraph 的消息通道）一般内置这类路由。

### 3. 结论融合与投票机制

当多个 Agent 给出不同结论，需要「收敛」：

- **投票（Voting）**：多个 Agent 独立回答，多数票胜出（类似 Self-Consistency，见提示词工程）。
- **裁判汇总（Judge/Synthesis）**：由一个汇总 Agent 读所有结论，综合成最终答案，并能指出分歧点。
- **加权融合**：按 Agent 置信度/历史准确率加权。

### 4. 冲突的类型与处理

| 冲突类型 | 表现 | 处理 |
| -- | -- | -- |
| 事实冲突 | A 说价格 100，B 说 200 | 引入可信源/工具二次核实 |
| 目标冲突 | 两个 Agent 优化方向矛盾 | Manager 统一优先级 |
| 资源冲突 | 同时写同一份状态 | 加锁 / 串行化 / 版本号 |
| 死循环 | 两 Agent 反复互相推翻 | 设最大轮次，强制收敛 |

### 经验

- 简单协作用「黑板 + 汇总 Agent」足够；
- 冲突处理的核心是「**有一个最终裁决者**」（Manager 或 Judge），否则永远达不成一致；
- 通信轮次要有上限，防止 Agent 们聊到天荒地老（成本爆炸）。
