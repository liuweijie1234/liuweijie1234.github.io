## 8.1 评测方法

不评测的 Agent 优化都是玄学。先建立可量化的评测体系，才知道「改了有没有用」。

### 1. 端到端任务成功率

最核心的指标：给定一批真实任务，Agent 最终**答对/办成**的比例。

- 构造测试集：覆盖典型场景 + 边界场景 + 历史 bad case；
- 自动判定（能定的，如「代码跑通」「订单查到」）或人工打分（开放任务）；
- 每次提示词/模型改动后重跑，对比成功率变化。

### 2. 工具调用准确率

Agent 类系统特有关注点：

- **选对工具**：该调 A 没调 B（如该查订单却去搜网页）；
- **参数正确**：参数名/值/类型对不对；
- **调用时序**：多工具时顺序、依赖是否正确。

可用「预期工具序列」和「实际序列」做比对打分。

### 3. 轨迹评估（Trajectory Eval）

不仅看结果，还看**过程对不对**：

- 有没有走冗余步（成本浪费）；
- 有没有危险操作（未授权调用）；
- 思考链是否合理。

人工抽检轨迹 + 用 LLM 当裁判（LLM-as-Judge）批量打分，是性价比高的做法。

### 4. 基准测试集

直接用业界标准 benchmark 横向对比能力：

| 基准 | 考察 |
| -- | -- |
| WebArena | 网页环境多步任务 |
| SWE-bench | 真实 GitHub issue 改代码 |
| AgentBench | 多环境综合 Agent 能力 |
| GAIA | 需多工具的真实问题 |

注意：benchmark 和实际业务有 gap，适合「选型对比」，上线前仍以**自有业务测试集**为准。

### 5. A/B 与人工 Bad Case 评审

- **A/B 测试**：新旧两版并行，用同一测试集量化差异；
- **Bad Case 评审会**：定期把翻车的案例拉出来，归类根因（检索差？提示词弱？工具不稳？），逐个攻破。

### 经验

- 先攒一个「黄金测试集」（50~200 条覆盖主场景），把它当回归测试守门员；
- 指标不要只看最终结果，工具准确率 + 轨迹质量能更早暴露问题；
- 评测集本身要随业务更新，别用半年前的旧集。
