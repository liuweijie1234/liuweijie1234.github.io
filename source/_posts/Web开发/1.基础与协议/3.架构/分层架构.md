## 一、为什么要分层

分层把系统按**职责**切分，降低耦合、便于测试与维护。经典 Web 后端分层：

```
表现层(Controller/View) → 业务逻辑层(Service) → 数据访问层(DAO/Repository) → 数据库
```

## 二、各层职责

- **表现层**：接收请求、参数校验、选择响应（详见 `2.Web框架` 各框架视图）。
- **业务逻辑层**：核心规则、事务边界，**不依赖具体框架**。
- **数据访问层**：封装 DB 操作，屏蔽 ORM 细节。
- **模型层**：领域实体（Django Model / SQLAlchemy Model）。

## 三、与 MVC/MTV 的关系

- Django 的 MTV：`Model`（模型）、`Template`（视图）、`View`（控制）→ 见 `2.开发模式`。
- 在 MTV 之上再抽 `Service` 层，可避免「胖视图/胖模型」。

## 四、依赖方向

上层依赖下层，下层不反向依赖。业务层依赖**抽象接口**而非具体实现，便于替换（如测试时换内存 DAO）。

## 五、常见反模式

- 视图里写大量 SQL/业务（胖视图）。
- 模型塞满跨领域逻辑（胖模型）。
- 不分层的「全在一个文件」，难以测试。

## 六、最佳实践

- 视图只做「取参 → 调 Service → 选响应」。
- 事务放在 Service 层用 `@transaction.atomic` 管理。
- 跨聚合的复杂流程用应用服务编排。
- 保持业务层与 Web 框架解耦，便于复用与测试。
