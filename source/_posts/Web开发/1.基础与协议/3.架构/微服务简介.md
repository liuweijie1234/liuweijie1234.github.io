## 一、单体 vs 微服务

- **单体（Monolith）**：所有功能在一个进程/代码库。简单、易部署，但随规模变大耦合严重、发布慢。
- **微服务**：按业务域拆成**独立部署、独立数据库**的小服务，通过 RPC/HTTP 通信。

## 二、核心特征

- 单一职责、独立部署。
- 去中心化数据管理（每服务自有 DB）。
- 通过 API 网关 / 消息队列通信。
- 技术栈可按服务选择。

## 三、关键组件

| 组件 | 作用 |
|------|------|
| API Gateway | 统一入口、鉴权、限流 |
| 服务注册与发现 | 动态寻址（Consul/Nacos） |
| 配置中心 | 集中配置 |
| 消息队列 | 异步解耦（见 `3.异步任务与消息队列/1.Celery`、RabbitMQ/Kafka） |
| 链路追踪 | 分布式调用观测（Jaeger/Zipkin） |
| 容器编排 | K8s 调度 |

## 四、通信方式

- 同步：REST / gRPC。
- 异步：消息队列（解耦、削峰）。

## 五、什么时候用

- 团队/业务规模大、需独立扩容与发布。
- 早期项目先用**模块化单体**，过度拆分反而增加运维成本。

## 六、最佳实践

- 先单体后微服务的渐进式演进。
- 明确服务边界（DDD 限界上下文）。
- 基础设施（网关、监控、链路）先行，不然「分布式单体」更痛。
- 数据库按服务拆分，避免共享库导致的隐式耦合。
