## 一、HTTP 状态码规范

用标准状态码让客户端无需解析 body 即可判断结果：

| 范围 | 含义 | 常见 |
|------|------|------|
| 2xx | 成功 | 200 OK、201 Created、204 No Content |
| 3xx | 重定向 | 301、304 Not Modified |
| 4xx | 客户端错误 | 400 Bad Request、401 Unauthorized、403 Forbidden、404 Not Found、409 Conflict、422 Unprocessable Entity |
| 5xx | 服务端错误 | 500、502、503 |

## 二、典型用法

- `201`：创建成功（配合 `Location` 头返回新资源 URI）。
- `202`：已接受异步处理（配合后台任务，见 FastAPI `7.后台任务与异步`）。
- `204`：成功但无内容返回（如 DELETE）。
- `400` vs `422`：参数格式错用 `400`，语义校验失败用 `422`（FastAPI 默认）。
- `401` 未认证 vs `403` 无权限：先登录 vs 已登录但无权。

## 三、版本控制策略

API 演进不可避免，版本化避免破坏旧客户端：

| 方式 | 示例 | 评价 |
|------|------|------|
| URI 版本 | `/api/v1/users` | 直观、易调试（推荐起步） |
| 请求头 | `Accept: application/vnd.myapi.v1+json` | 干净但不便调试 |
| 查询参数 | `/users?version=1` | 不推荐 |

## 四、演进建议

- 新功能加字段保持向后兼容（老客户端忽略新字段）。
- 破坏性变更再升主版本（`v2`）。
- 废弃旧版本提前公告并给迁移期。

## 五、错误响应结构

```json
{
  "error": {
    "code": "INVALID_PARAM",
    "message": "字段 price 必须为正数",
    "field": "price"
  }
}
```

## 六、最佳实践

- 状态码要语义正确，不要一律 200 + 错误码在 body。
- 版本放 URI 前缀，简单清晰。
- 文档同步更新（FastAPI 自带 `/docs` 很省心）。
- 用 `422` 表达校验失败，与 `400` 区分。
