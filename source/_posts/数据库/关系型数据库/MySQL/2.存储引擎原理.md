# MySQL 存储引擎原理

> 存储引擎是 MySQL 的「数据如何落盘、如何索引、如何保证事务」的核心。自 5.5 起默认引擎为 **InnoDB**，本文从架构到关键组件逐层拆解。

---

## 1. 存储引擎是什么 & 常见引擎对比

MySQL 采用**插件式存储引擎**架构：SQL 层（连接、解析、优化）与存储层（存取、索引、事务）解耦，不同表可用不同引擎。

| 特性 | InnoDB | MyISAM |
| --- | --- | --- |
| 事务 | ✅ 支持 ACID | ❌ |
| 外键 | ✅ | ❌ |
| 锁粒度 | 行锁 | 表锁 |
| MVCC | ✅ | ❌ |
| 崩溃恢复 | ✅（redo） | ❌ |
| 全文索引 | ✅（5.6+） | ✅ |
| 聚簇索引 | ✅ | ❌（堆表） |
| 适用场景 | 高并发 OLTP | 读多写少、静态表 |

```sql
SHOW ENGINES;                       -- 查看支持的引擎
SELECT table_name, engine FROM information_schema.tables WHERE table_schema='test';
ALTER TABLE t ENGINE=InnoDB;        -- 改表引擎
```

> 新项目一律用 InnoDB；MyISAM 仅存于老系统，且不支持崩溃恢复，已逐步淘汰。

## 2. InnoDB 整体架构

InnoDB 分**内存结构**与**磁盘结构**两大部分：

```
            ┌─────────────────────────────┐
  内存      │  Buffer Pool  │ Log Buffer  │
            │  (数据/索引缓存) │ (redo缓冲) │
            └───────────────┬─────────────┘
                            │ 异步刷盘
  磁盘      ┌───────────────┼───────────────────────┐
            │  ibd 表空间   │ redo log │ undo log    │
            │ (数据+索引)   │ (物理)   │ (逻辑回滚)  │
            └───────────────┴──────────┴─────────────┘
```

### 2.1 内存结构

- **Buffer Pool**：缓存表数据与索引页，是性能核心。读时先查缓冲，未命中再从磁盘读入；写时先改缓冲（脏页），由后台线程刷盘。
- **Change Buffer**：对非唯一二级索引的写操作，若页不在缓冲中，先缓存变更，待页被读取时合并（减少随机 IO）。
- **Adaptive Hash Index（AHI）**：对频繁访问的索引前缀自动建哈希索引，加速等值查询。
- **Log Buffer**：redo log 的写入缓冲，`innodb_log_buffer_size` 控制。

### 2.2 磁盘结构

- **表空间（Tablespace）**：系统表空间 `ibdata1` + 各表独立 `.ibd`（开启 `innodb_file_per_table` 时）。
- **redo log**：物理日志，记录「页做了什么修改」，用于崩溃恢复。
- **undo log**：逻辑日志，记录事务前的数据镜像，用于回滚与 MVCC。

## 3. Buffer Pool 工作原理

Buffer Pool 以 **页（16KB）** 为管理单位，内部用 **LRU 链表** 管理冷热数据：

- 链表分 **young 区（热，5/8）** 与 **old 区（冷，3/8）**；
- 新读入的页先放 old 区头部；
- 只有页在 old 区停留超过 `innodb_old_blocks_time`（默认 1s）再次被访问，才晋升到 young 区。

> 该设计避免全表扫描把热点数据瞬间冲掉（扫描的页只在 old 区短暂停留即被淘汰）。

关键参数：

```ini
innodb_buffer_pool_size = 4G     # 物理内存的 60%~80%
innodb_buffer_pool_instances = 8 # 大于 1GB 时拆分，减少锁竞争
```

## 4. 事务日志：redo / undo

### 4.1 redo log（重做日志）—— 保证持久性

- 采用 **WAL（Write-Ahead Logging）**：事务提交时，先写 redo 再返回成功，脏页异步刷盘。
- 环形写入，由 `innodb_log_file_size` 与文件数控制。
- 崩溃重启时，用 redo 把未刷盘的已提交事务重放，保证**已提交数据不丢**。

`innodb_flush_log_at_trx_commit` 控制刷盘策略：

| 值 | 行为 | 安全性 |
| --- | --- | --- |
| 1（默认） | 每次提交都 fsync | 不丢（强一致） |
| 2 | 写文件缓存，每秒 fsync | 宕机可能丢 1s |
| 0 | 每秒写并 fsync | 宕机可能丢 1s |

### 4.2 undo log（回滚日志）—— 保证原子性 & 支撑 MVCC

- 事务修改前，把旧值写入 undo log；
- 回滚时反向应用 undo 即可恢复；
- 旧版本链供 MVCC 的 `ReadView` 读取历史快照（详见 `4.事务与并发控制`）。

---

## 5. 双写缓冲（Doublewrite Buffer）

- 脏页刷盘时，先写 **doublewrite buffer**（顺序写），再写实际数据页；
- 防止「部分写失效」（页写到一半断电，页损坏）；
- 崩溃恢复时可从 doublewrite 拷贝完整页重建。

---

## 6. 表空间与页结构

- **段（Segment）→ 区（Extent，1MB=64 页）→ 页（Page，16KB）** 三级管理；
- 行记录格式：`Compact` / `Dynamic`（8.0 默认），`NULL` 不占空间，大字段溢出到溢出页；
- 每行有隐藏列：`DB_TRX_ID`（最后修改事务 ID）、`DB_ROLL_PTR`（指向 undo 版本链指针）、`DB_ROW_ID`（无主键时自动生成）。

---

## 7. 自增与写入优化

- `innodb_autoinc_lock_mode` 控制自增锁：
  - `0`：语句级表锁（安全但慢）；
  - `1`（5.7 默认）：混合；
  - `2`（8.0 默认）：无锁，性能最好，但主从复制（statement 格式）可能不一致。
- 写入密集场景调大 `innodb_log_file_size`（如 1G），减少 checkpoint 抖动。

---

## 8. 小结

理解 InnoDB 的关键在于：**Buffer Pool 是性能中枢，redo 保持久、undo 保原子并支撑 MVCC，doublewrite 防页损坏**。下一章 **索引原理** 将看到，这一切都是为了让 B+ 树索引的页能高效缓存与更新。
