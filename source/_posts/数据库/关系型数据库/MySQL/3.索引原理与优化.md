# MySQL 索引原理与优化

> 索引是 MySQL 性能的第一杠杆。本文从「为什么快」的 B+ 树讲起，逐层拆解聚簇/二级索引、联合索引与最左前缀、覆盖索引、索引失效等高频考点。

---

## 1. 为什么需要索引

无索引时只能 **全表扫描（All）**，数据量越大越慢。索引相当于书的目录，把 `O(N)` 查找降为 `O(log N)`。

InnoDB 的索引底层是 **B+ 树**。

---

## 2. B+ 树结构（与 B 树的区别）

**B+ 树特征**：

- 非叶子节点只存**键值 + 指针**，不存数据，因此单页能容纳更多键 → 树更矮胖，减少 IO 次数；
- 所有**数据都在叶子节点**，且叶子节点用**双向链表**串联；
- 等值查询与范围查询（`BETWEEN`、`ORDER BY`）都能高效命中。

> 对比 B 树：B 树的非叶子节点也存数据，导致单页键少、树更高；且无法像 B+ 树那样用链表做范围扫描。

```
        [ 10 | 30 ]            ← 非叶子，只存键
       /     |      \
  [1,5]  [11,20]  [31,40]      ← 叶子，存数据 + 双向链表
```

InnoDB 页默认 16KB，三层 B+ 树可存约 **两千万** 行，绝大多数查询只需 2~3 次磁盘 IO。

---

## 3. 聚簇索引 vs 二级索引

### 3.1 聚簇索引（Clustered Index）

- InnoDB **主键即聚簇索引**，叶子节点存**整行数据**；
- 表数据按主键顺序物理组织（索引即数据）；
- 若无显式主键，则选第一个唯一非空索引；再无则用隐式 `DB_ROW_ID`。

### 3.2 二级索引（Secondary Index）

- 叶子节点存 **索引列值 + 主键值**（不是行指针！）；
- 通过二级索引查非索引列时，需**回表**：用主键再去聚簇索引取整行。

```
二级索引叶子: [name='Tom' → pk=5]
                 │ 回表
                 ▼
聚簇索引叶子:   [pk=5 → (Tom, 25, ...)]   ← 整行
```

> 设计启示：**主键应短而递增**（如 BIGINT 自增），过长主键会让所有二级索引膨胀。

---

## 4. 索引类型

| 类型 | 说明 |
| --- | --- |
| 普通索引 `INDEX` | 最基础 |
| 唯一索引 `UNIQUE` | 列值不重复，允许 NULL |
| 主键索引 `PRIMARY KEY` | 聚簇，非空唯一 |
| 组合索引 | 多列联合，遵循最左前缀 |
| 全文索引 `FULLTEXT` | 文本检索（8.0+ 用 ngram 支持中文） |
| 前缀索引 | 对长字符串取前 N 字节，省空间 |

```sql
CREATE INDEX idx_name ON user(name);
CREATE UNIQUE INDEX uk_email ON user(email);
CREATE INDEX idx_age_name ON user(age, name);
ALTER TABLE user DROP INDEX idx_name;
SHOW INDEX FROM user;
```

## 5. 联合索引与最左前缀原则

联合索引 `(a, b, c)` 在 B+ 树中按 **a→b→c 字典序** 排序，相当于 `(a)`、`(a,b)`、`(a,b,c)` 三个索引。

```sql
-- 命中（使用了 a, b）
WHERE a=1 AND b=2;

-- 命中（使用了 a, b, c）
WHERE a=1 AND b=2 AND c=3;

-- 只用 a（b 用了范围，c 失效）
WHERE a=1 AND b>2 AND c=3;

-- 失效（无 a，跳过了最左列）
WHERE b=2 AND c=3;
```

> **底层原理**：B+ 树先按 a 排序，a 相同才按 b，b 相同才按 c。没有 a 就无法定位区间，只能全表扫描。`LIKE 'abc%'` 走前缀，`LIKE '%abc'` 不走。

---

## 6. 覆盖索引（避免回表）

若查询的**所有列都在索引中**，无需回表：

```sql
-- idx_age_name = (age, name)，查询只取这两列 → 覆盖索引
SELECT age, name FROM user WHERE age = 25;

-- 若 SELECT * 需要回表，可能更慢
SELECT * FROM user WHERE age = 25;
```

> 用 `EXPLAIN` 看 `Extra: Using index` 即表示命中覆盖索引。

---

## 7. 索引下推（ICP, Index Condition Pushdown）

MySQL 5.6+ 支持：在**存储引擎层**就用索引中的列过滤，减少回表次数。

```sql
-- idx = (age, name)
SELECT * FROM user WHERE age=25 AND name LIKE 'T%';
-- 没有 ICP：先按 age 回表取行，再在 Server 层判断 name
-- 有 ICP：在引擎层就用 name 过滤，少回表
```

---

## 8. 索引失效的常见场景

1. **对列做函数/运算**：`WHERE YEAR(created)=2024`（应改范围）；
2. **隐式类型转换**：`WHERE phone = 13800000000`（phone 是字符串，传数字会转）；
3. **前导模糊**：`LIKE '%abc'`；
4. **违反最左前缀**：联合索引跳过最左列；
5. **OR 连接非索引列**：`WHERE a=1 OR b=2`（b 无索引则全表）；
6. **优化器认为全表更快**：数据量极小或区分度极低（如性别）。

---

## 9. 索引设计原则

- **高区分度列放联合索引前面**（`COUNT(DISTINCT col)/COUNT(*)` 越大越好）；
- 优先建在 `WHERE`、`JOIN ON`、`ORDER BY`、`GROUP BY` 涉及的列；
- 避免过多索引：增删改都要维护索引，写性能下降；
- 长字符串用**前缀索引**；
- 利用**覆盖索引**减少回表；
- 用 `EXPLAIN` 验证，关注 `type`、`key`、`rows`、`Extra`。

---

## 10. 小结

索引的本质是 **B+ 树 + 聚簇组织 + 最左前缀**。记住三条心法：**主键短而递增、查询走覆盖、避免失效**。下一章用 `EXPLAIN` 把执行计划看透，把索引真正用对。
