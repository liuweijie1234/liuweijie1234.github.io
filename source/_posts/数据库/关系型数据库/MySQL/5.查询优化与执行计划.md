# MySQL 查询优化与执行计划

> 慢 SQL 是线上事故的头号来源。本文讲清「如何定位慢查询」与「如何用 EXPLAIN 读懂执行计划」，并给出分页、JOIN、索引失效等高频优化套路。

---

## 1. 定位慢查询

### 1.1 慢查询日志

```ini
slow_query_log = ON
slow_query_log_file = /var/log/mysql/slow.log
long_query_time = 1          # 超过 1 秒记日志
log_queries_not_using_indexes = ON   # 没走索引的也记
```

实时查看：

```sql
SHOW VARIABLES LIKE 'slow_query%';
SHOW VARIABLES LIKE 'long_query_time';
```

### 1.2 当前活跃查询

```sql
SHOW FULL PROCESSLIST;                 -- 看正在跑的 SQL、State、Time
SELECT * FROM information_schema.PROCESSLIST
WHERE TIME > 5 ORDER BY TIME DESC;    -- 找长事务/慢查询
-- 杀掉可疑连接
KILL 12345;
```

## 2. EXPLAIN 执行计划详解

```sql
EXPLAIN SELECT * FROM user WHERE age = 25 AND name LIKE 'T%';
```

关键列：

| 列 | 含义 | 关注点 |
| --- | --- | --- |
| `id` | 查询序号 | 越大越先执行，相同按序 |
| `select_type` | 查询类型 | SIMPLE / PRIMARY / SUBQUERY / DERIVED |
| `type` | 访问类型 | **system > const > eq_ref > ref > range > index > ALL** |
| `key` | 实际用到的索引 | NULL 表示没走索引 |
| `rows` | 预估扫描行数 | 越小越好 |
| `Extra` | 额外信息 | `Using index`(覆盖) / `Using where` / `Using filesort` / `Using temporary` |

### 2.1 type 等级（性能从好到差）

- `const`：主键/唯一索引等值，至多一行；
- `eq_ref`：JOIN 时主键/唯一索引关联；
- `ref`：非唯一索引等值；
- `range`：索引范围（BETWEEN、IN、>）；
- `index`：全索引扫描（比 ALL 好，因索引更小）；
- `ALL`：**全表扫描**，必须优化。

### 2.2 危险 Extra

- `Using filesort`：无法用索引排序，需额外排序（内存/磁盘），应建排序索引；
- `Using temporary`：用了临时表（GROUP BY/ORDER BY 不同列），尽量消除。

---

## 3. 索引优化套路

1. **遵循最左前缀**，联合索引顺序按区分度与查询频率排；
2. **避免对列做函数/运算/隐式转换**（见 第 3 章 失效场景）；
3. **覆盖索引**减少回表；
4. 范围查询（`>`、`BETWEEN`）后的列在联合索引中失效，把等值列前置；
5. 用 `ORDER BY`/`GROUP BY` 的列尽量与 WHERE 同属一个索引。

```sql
-- 反例：对列套函数 → 索引失效
SELECT * FROM orders WHERE DATE(created) = '2024-01-01';
-- 正解：改写为范围
SELECT * FROM orders
WHERE created >= '2024-01-01' AND created < '2024-01-02';
```

## 4. 大分页优化（LIMIT 100000, 10 为什么慢）

`LIMIT offset, n` 要**先排序再跳过 offset 行**，offset 越大越慢（扫描 10 万行只为取 10 行）。

### 4.1 延迟关联（先索引后回表）

```sql
-- 慢
SELECT * FROM orders ORDER BY id LIMIT 100000, 10;

-- 快：子查询只扫索引拿主键，再 JOIN 回表
SELECT a.* FROM orders a
JOIN (SELECT id FROM orders ORDER BY id LIMIT 100000, 10) b ON a.id = b.id;
```

### 4.2 游标/书签法（上一页最大值）

```sql
-- 上一页最后一条 id = 100000
SELECT * FROM orders WHERE id > 100000 ORDER BY id LIMIT 10;
```

> 只能连续翻页，不能跳页，但性能恒定，适合「下拉加载更多」。

### 4.3 瀑布流（时间游标）

```sql
SELECT * FROM orders
WHERE created < '2024-06-01 12:00:00'
ORDER BY created DESC LIMIT 20;
```

## 5. JOIN 与子查询优化

- **小表驱动大表**：`SELECT ... FROM 小表 JOIN 大表 ON ...`，让外层循环次数少；
- 关联字段**必须建索引**（否则笛卡尔积级膨胀）；
- 能用 JOIN 就别用 `IN (子查询)`，后者常改写为 JOIN / 半连接；
- `EXISTS` 适合「存在即返回」，比 `IN` 在大集合时更高效。

---

## 6. 其他优化手段

- **统计信息/直方图**：`ANALYZE TABLE t;` 更新统计，帮助优化器选对索引；
- **分页统计去 count(*)** 大表用近似值或缓存；
- **避免 `SELECT *`**：减少 IO 与回表；
- **批量操作**代替循环单条；
- **冷热分离 / 归档**老数据。

---

## 7. 小结

优化的闭环：**慢日志定位 → EXPLAIN 看 type/key/rows/Extra → 加对索引/改写法 → 再 EXPLAIN 验证**。下一章进入**复制与高可用**，解决单点故障与读写扩展。
