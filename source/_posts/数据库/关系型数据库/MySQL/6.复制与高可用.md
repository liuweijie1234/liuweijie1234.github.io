# MySQL 复制与高可用

> 单机 MySQL 既扛不住读扩展，也存在单点故障。复制（Replication）是读写分离、备份、高可用的基石。本文厘清主从/主备/主主、复制原理、延迟根因与高可用方案。

---

## 1. 三种拓扑：主从 / 主备 / 主主

| 拓扑 | 结构 | 用途 |
| --- | --- | --- |
| **主从（Master-Slave）** | 1 主写，N 从读 | 读写分离、负载分担 |
| **主备（Master-Standby）** | 1 主写，1 备待命 | 高可用、故障切换 |
| **主主（Master-Master）** | 双主互写 | 双活（易冲突，慎用） |

> 主备与主从技术相同，**语义差异**在于：主备的备机平时不承接流量，仅故障切换；主从的从库常态承接读流量。

---

## 2. 主从复制原理

基于 **binlog（二进制日志）**，异步复制三步走：

```
Master                                        Slave
  │                                             │
  ├─ 事务提交，写 binlog                         │
  │                                             │
  ├─ <Binlog Dump> 推送给 Slave ──────────────► │ IO 线程写 relay log(中继日志)
  │                                             │
  │                                   ◄──────── │ SQL 线程回放 relay log → 数据
```

- **binlog_format**：`STATEMENT`（SQL 语句）、`ROW`（行变更，默认，最安全）、`MIXED`；
- **IO 线程**：拉取 master binlog 写入 relay log；
- **SQL 线程**：重放 relay log，应用变更。

### 2.1 复制模式

| 模式 | 行为 | 数据一致性 |
| --- | --- | --- |
| 异步（默认） | 主提交即返回，不等从 | 主宕可能丢已提交数据 |
| 半同步 | 至少 1 个从收到 relay 才返回 | 折中 |
| 全同步 | 所有从都应用完才返回 | 强一致，性能差 |

```ini
# 主库开启 binlog
[mysqld]
log-bin = mysql-bin
server-id = 1
binlog_format = ROW

# 从库
server-id = 2
relay-log = relay-bin
read_only = ON        # 从库只读（super 用户仍写，8.0 用 super_read_only）
```

```sql
-- 从库配置主库
CHANGE MASTER TO
  MASTER_HOST='10.0.0.1', MASTER_USER='repl',
  MASTER_PASSWORD='pass', MASTER_LOG_FILE='mysql-bin.000001',
  MASTER_LOG_POS=154;
START SLAVE;
SHOW SLAVE STATUS\G     -- 看 Slave_IO_Running / Slave_SQL_Running
```

### 2.2 GTID 复制（推荐）

全局事务 ID，自动定位位点，故障切换无需手动算 `MASTER_LOG_POS`：

```ini
gtid_mode = ON
enforce_gtid_consistency = ON
```

## 3. 读写分离

把写落主库、读走从库，提升读吞吐：

- **代码层**：ORM/数据源路由（如 Spring `@Transactional(readOnly=true)` 走从）；
- **中间件**：MyCat、ProxySQL、ShardingSphere-Proxy 透明路由；
- **负载均衡**：从库间轮询/权重。

---

## 4. 主从延迟（高频坑）

### 4.1 原因

- 从库 **SQL 线程单线程**回放，主库高并发写入时追赶不及（5.7+ 支持**并行复制** `slave_parallel_workers` 缓解）；
- 从库有**大查询/大事务/备份**占资源；
- 主库执行**大事务**（如一次性删百万行），binlog 传到从库一次性重放；
- 网络抖动、从库硬件弱于主库。

### 4.2 解决方案

1. **并行复制**：`slave_parallel_type = LOGICAL_CLOCK`；
2. **拆大事务**为小批；
3. 避免从库跑重报表，独立分析库；
4. 业务容忍：读刚写入的数据走主库（读写分离下的"读己写"）；
5. 半同步 + 强一致中间件（如要求严格一致时直接读主）。

```sql
SHOW SLAVE STATUS\G        -- Seconds_Behind_Master 看延迟秒数
```

## 5. 高可用方案

| 方案 | 原理 | 特点 |
| --- | --- | --- |
| **MHA** | 管理节点监测主库，自动选最新从库提升为主 | 经典，社区成熟 |
| **Orchestrator** | 基于拓扑的自动 failover，支持 Raft | 功能强 |
| **MGR / InnoDB Cluster** | 组复制（Paxos），多主/单主 | 官方原生 |
| **Keepalived + VIP** | 双机热备漂移虚拟 IP | 简单 |

> 现代推荐 **MySQL InnoDB Cluster（MGR）** 或 **Orchestrator + 半同步** 组合。

---

## 6. 小结

复制 = binlog 流式同步；高可用 = 复制 + 自动 failover；读写分离 = 复制 + 流量路由。下一章 **分布式与分库分表** 解决单库容量与写入瓶颈。
