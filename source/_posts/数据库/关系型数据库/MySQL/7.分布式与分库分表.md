# MySQL 分布式与分库分表

> 单库的单表行数超过千万、写入 QPS 触顶、磁盘/连接成为瓶颈时，就要考虑拆分。本文讲清垂直/水平拆分、分片键、全局 ID 与分布式事务。

---

## 1. 什么时候需要分库分表

| 信号 | 建议 |
| --- | --- |
| 单表行数 > 千万且持续增 | 水平拆分 |
| 单库磁盘/连接瓶颈 | 分库 |
| 写入 QPS 高、主从延迟大 | 分库 + 多主 |
| 仅是某些大字段拖慢 | 垂直拆分（冷热分离） |

> 先优化索引、SQL、架构，**不要过早分表**。分表会带来跨分片查询、分布式事务等复杂度。

---

## 2. 垂直拆分 vs 水平拆分

### 2.1 垂直拆分

- **垂直分库**：按业务域把表分到不同库（用户库、订单库、商品库）；
- **垂直分表**：把大表的「宽列/大字段」拆到扩展表（如 `user` 与 `user_profile`）。
- 优点：业务清晰、冷热分离；缺点：跨库 JOIN 需应用层聚合。

### 2.2 水平拆分（分库分表）

- 同一张表按**分片键（sharding key）**把数据分布到多个库/表；
- 表结构相同，数据按规则路由。

---

## 3. 分片键与分片算法

### 3.1 分片键选择（最关键）

好的分片键应满足：**高频查询条件包含它、数据分布均匀、尽量避免跨片**。

- 订单表：用 `user_id` 分片（查"我的订单"只落一个分片），而非 `order_id`；
- 若按 `order_id` 查多，则加映射表（`order_id → user_id`）。

### 3.2 分片算法

| 算法 | 说明 | 优点 / 缺点 |
| --- | --- | --- |
| 哈希取模 `hash(key) % N` | 均匀分布 | 扩容需迁移大量数据 |
| 范围分片 | 按时间/ID 区间 | 易扩容、易冷热；易数据倾斜 |
| 一致性哈希 | 环上映射 | 扩容只迁移少量 |
| 基因法 | 分片位嵌入 ID | 避免额外映射 |

---

## 4. 全局唯一 ID

分片后自增主键冲突，需全局 ID：

- **Snowflake**：41 位时间戳 + 10 位机器 + 12 位序列，趋势递增、毫秒级唯一；
- **号段（Segment）**：从发号器批量取一段区间，本地分配，减少 RPC；
- **UUID**：简单但无序、索引碎片大，不推荐做主键；
- **Redis / Leaf**：美团 Leaf、滴滴 Tinyid 等成熟方案。

> 主键建议 **BIGINT 趋势递增**，契合 InnoDB 聚簇索引顺序写，减少页分裂。

---

## 5. 分布式事务

跨库操作无法靠单机事务保证一致：

| 方案 | 思路 | 适用 |
| --- | --- | --- |
| 2PC（两阶段提交） | 协调者 Prepare → Commit | 强一致、性能差、阻塞 |
| TCC | Try/Confirm/Cancel 业务补偿 | 高并发、需改造业务 |
| **消息队列最终一致** | 本地事务写消息表 → MQ → 消费 | 最常用，容忍短暂不一致 |
| Saga | 长事务拆补偿链 | 跨多服务 |

> 多数业务用「本地事务 + 可靠消息（事务消息/RocketMQ）」实现最终一致，避免 2PC 的性能与可用性代价。

---

## 6. 分库分表中间件

| 中间件 | 类型 | 特点 |
| --- | --- | --- |
| **ShardingSphere** | JDBC 代理 / Proxy | 生态全、社区活跃 |
| **MyCat** | Proxy 代理 | 老牌、配置式 |
| Vitess | 集群方案 | YouTube 开源，K8s 友好 |

> 中间件透明化分片路由、结果归并、分布式 ID，但对复杂 SQL（跨片 JOIN、子查询、聚合）支持有限，需业务配合。

---

## 7. 拆分后的典型难题

- **跨片查询/分页/排序**：需在中间件或应用层**归并**（`ORDER BY`+`LIMIT` 各片取 Top N 再合并）；
- **跨片 JOIN**：冗余字段、广播表、应用层聚合；
- **分布式事务**：见第 5 节；
- **扩容**：一致性哈希/号段降低迁移成本。

---

## 8. 小结

分库分表是「解决容量与并发」的终极手段，但代价是复杂度。决策顺序：**加索引/优化 SQL → 读写分离/升级硬件 → 垂直拆分 → 水平分表 → 上中间件**。下一章讲**配置与运维**，把实例跑稳、备份可靠。
