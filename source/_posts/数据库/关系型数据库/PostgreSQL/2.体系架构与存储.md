# PostgreSQL 体系架构与存储

理解 Postgres 的「进程模型 + 共享内存 + WAL + 堆表存储」，是掌握其性能与高可用的基础。与 MySQL 的「插件式存储引擎 + 单进程多线程」不同，Postgres 是**多进程 + 统一堆存储（Heap）**，且**无独立存储引擎概念**（核心即 Heap + 索引）。

## 一、整体架构（C/S + 多进程）

```
        客户端（psql / 应用）
              │ TCP
              ▼
        ┌─────────────┐
        │ postmaster  │   主进程：监听、接收连接、fork 后端
        └──────┬──────┘
     ┌─────────┼──────────┐
     ▼         ▼          ▼
  backend1  backend2  ...  bgwriter / walwriter / autovacuum / checkpointer
  (每连接     (每连接
   一个进程)  一个进程)
            │
            ▼
      ┌────────────┐
      │ 共享内存     │  shared_buffers / WAL buffer / 锁表
      └────────────┘
            │
            ▼
       磁盘：数据文件 / WAL / 日志
```

要点：

- **postmaster**：主守护进程，负责监听端口、为每个新连接 `fork` 一个 **backend 进程**。
- **每连接一进程**：进程隔离好、一个连接崩溃不影响其他；但高并发连接数多时内存/上下文切换开销大 → 需用 **PgBouncer** 连接池。
- **后台进程**：`background writer`（刷脏页）、`wal writer`（写 WAL）、`checkpointer`（做检查点）、`autovacuum`（回收死元组）、`archiver`（归档 WAL）。

## 二、内存结构

| 区域 | 作用 | 建议 |
| --- | --- | --- |
| `shared_buffers` | 共享缓冲，缓存数据页（类似 InnoDB Buffer Pool） | 设为 RAM 的 25% |
| `WAL buffer` | WAL 写缓冲，提交时刷盘 | 无需手动大调 |
| `work_mem` | 每个排序/哈希操作的私有内存 | 增大会加速排序但吃内存（×并发） |
| `maintenance_work_mem` | VACUUM/建索引等维护操作内存 | 可设较大 |

> 与 MySQL 不同：Postgres 没有「InnoDB 那样的独立引擎层」，存储管理（堆、索引、WAL）都在核心里。

## 三、物理存储：堆表（Heap）

- 数据以 **8KB 页（page/block）** 为单位存储（可编译为 4/16/32KB）。
- 表是**堆（Heap）** 结构：新行追加到任意有空间的页，没有「聚簇索引」概念（InnoDB 的聚簇在 Postgres 不存在）。
- 每行有 **行头（tuple header）**，含 `xmin`/`xmax`（事务 ID）用于 MVCC 版本控制，`ctid`（页号+行号，相当于行物理地址）。
- 表文件按 1GB 分段（`base/数据库OID/表OID.0`, `.1`...）。

```sql
-- 查看表物理信息
SELECT pg_relation_filepath('users');
SELECT * FROM pg_stat_user_tables WHERE relname='users';
```

## 四、WAL（Write-Ahead Logging，预写日志）

Postgres 的崩溃恢复与复制基石，原理与 InnoDB redo log 类似：**先写日志，再改数据**。

- WAL 记录所有数据修改，顺序追加写，保证持久性。
- 提交事务时，WAL 必须落盘（`synchronous_commit` 控制强度）。
- `wal_level` 决定 WAL 详细程度：`minimal` / `replica`（流复制所需）/ `logical`（逻辑复制所需）。
- **检查点（checkpoint）**：把 shared_buffers 中脏页刷到数据文件，并更新 `pg_control`，使恢复起点前移。

```ini
# postgresql.conf 关键
wal_level = replica
checkpoint_timeout = 5min
max_wal_size = 2GB
synchronous_commit = on    # on=强一致（慢但安全）；off=异步（快但可能丢最后事务）
```

> MVCC + WAL 的组合，使 Postgres 既能做时间点恢复（PITR），又能支撑流复制（第 7 章）。

## 五、MVCC 与死元组（关键概念）

Postgres 的 MVCC 通过**保留旧版本（死元组）** 实现：UPDATE = 标记旧行 `xmax` + 插入新行。旧版本对其它事务可见期间不能删除，导致：

- 表会膨胀（dead tuples 堆积）。
- 需要 **VACUUM** 回收空间、更新可见性映射（visibility map）。
- **autovacuum** 后台自动运行，但大表/高频更新需调参避免膨胀失控。

```sql
-- 查看表膨胀
SELECT schemaname, relname, n_dead_tup, n_live_tup
FROM pg_stat_user_tables ORDER BY n_dead_tup DESC;

-- 手动 vacuum
VACUUM (VERBOSE, ANALYZE) users;
```

## 六、TOAST（超长字段存储）

当行超过约 2KB，Postgres 用 **TOAST（The Oversized-Attribute Storage Technique）** 把大字段（text/jsonb/bytea）压缩或溢出到独立 TOAST 表，避免页过大。

## 七、与 MySQL 存储对比

| 维度 | PostgreSQL | MySQL (InnoDB) |
| --- | --- | --- |
| 进程模型 | 多进程（每连接一进程） | 单进程多线程 |
| 存储引擎 | 核心 Heap（无插件式） | 插件式（InnoDB 为主） |
| 索引组织 | 堆表 + 独立索引（无聚簇） | 聚簇索引（主键即数据） |
| MVCC 实现 | 多版本（死元组 + VACUUM） | undo 日志 + 回滚指针 |
| WAL | 原生 WAL | redo + binlog（双日志） |
| 事务 ID | 32 位 xid（需防回卷） | 无此概念 |
