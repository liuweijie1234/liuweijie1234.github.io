# PostgreSQL 索引

Postgres 的索引生态是关系库中**最丰富**的：不仅有标准 B-tree，还有 GIN、GiST、BRIN、Hash、SP-GiST，且支持**部分索引、表达式索引、覆盖索引（INCLUDE）**。理解各类索引的适用场景，是性能调优的核心。本文逐一拆解。

## 一、索引方法总览

| 方法 | 适用 |
| --- | --- |
| **B-tree**（默认） | 等值、范围、排序，绝大多数场景 |
| **GIN**（Generalized Inverted） | 多值/包含：数组、`jsonb`、`tsvector` 全文 |
| **GiST**（Generalized Search Tree） | 几何、范围、模糊、PostGIS 空间 |
| **BRIN**（Block Range INdex） | 超大表、按物理顺序线性相关的列（如时间） |
| **Hash** | 纯等值（PG10+ 支持 WAL 可复制，但一般用 B-tree 替代） |
| **SP-GiST** | 空间分区（四叉树、k-d 树等） |

## 二、B-tree（默认，万能）

```sql
CREATE INDEX idx_users_age ON users(age);
CREATE INDEX idx_users_name ON users(name);   -- 默认即 USING btree

-- 复合索引
CREATE INDEX idx_users_city_age ON users(city, age);
```

- 支持 `=`、`<`、`>`、`BETWEEN`、`LIKE '前缀%'`、`IS NULL`、排序。
- 遵循**最左前缀**：`(city, age)` 可服务 `city=` 与 `city= AND age=`，但单独 `age=` 走不了。
- 与 MySQL 类似，但 Postgres 的 B-tree 还是「唯一能支持 NULL 排序/不等式」的最通用结构。

## 三、GIN：多值与包含

GIN 是**倒排索引**，专为「一个键对应多个值」设计：

```sql
-- 数组
CREATE INDEX idx_tags ON posts USING gin(tags);

-- JSONB（路径 ops 更小更快，支持 @>）
CREATE INDEX idx_attrs ON products USING gin(attrs jsonb_path_ops);

-- 全文检索 tsvector
CREATE INDEX idx_tsv ON articles USING gin(tsv);
```

适用操作：`@>`（包含）、`?`（键存在）、`&&`（重叠）、全文 `@@`。
代价：写入较慢（需更新倒排条目），适合**读多写少**的文档/标签场景。

## 四、GiST：通用搜索树

GiST 是框架型索引，支持**非等值、几何、范围、模糊**：

```sql
-- 范围重叠查询
CREATE INDEX idx_during ON bookings USING gist(during);

-- 几何/空间（配合 PostGIS）
CREATE INDEX idx_geom ON roads USING gist(geom);
```

适合 `&&`（重叠）、`<<`（左邻）、距离（`<->`）等几何/范围操作。相比 GIN，GiST 写入更快、查询稍慢。

## 五、BRIN：超大数据块的轻量索引

BRIN 只记录**每个数据块范围的极值（min/max）**，体积极小，适合「列值随物理插入顺序单调」的大表（如按时间追加的日志）：

```sql
CREATE INDEX idx_log_ts ON logs USING brin(created_at);
```

- 索引可能只有几十 KB（对比 B-tree 几十 MB）。
- 仅对「物理顺序与索引列相关」有效；若数据被打乱（如 UUID 主键），BRIN 失效。
- 适合 PB 级时序/日志表的轻量加速。

## 六、部分索引（Partial Index）

只对满足条件的行建索引，节省空间、提升写入：

```sql
-- 只为「未支付」订单建索引
CREATE INDEX idx_unpaid ON orders(order_no)
WHERE status = 'UNPAID';
```

查询 `WHERE status='UNPAID' AND order_no=...` 可命中。

## 七、表达式索引（Expression Index）

对函数/表达式结果建索引，加速带函数的查询：

```sql
-- 按邮箱小写查
CREATE INDEX idx_lower_email ON users(lower(email));
SELECT * FROM users WHERE lower(email) = 'a@b.com';

-- 按日期截断查某天
CREATE INDEX idx_day ON logs(date_trunc('day', created_at));
```

## 八、覆盖索引与 INCLUDE（PG11+）

```sql
-- 索引自身包含 extra 列，避免回表
CREATE INDEX idx_cover ON users(city) INCLUDE (name, age);
-- 查询只取 city/name/age 时，索引即可返回（Index Only Scan）
```

`EXPLAIN` 中看到 `Index Only Scan` 即命中覆盖，性能极佳。

## 九、执行计划与索引诊断

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM users WHERE city='北京' AND age > 18;
```

- `Index Scan` / `Index Only Scan`：健康。
- `Seq Scan`：全表扫描，需警惕。
- `Bitmap Index Scan + Bitmap Heap Scan`：先位图定位再回表，常见于多条件。
- `Buffers: shared hit/read`：看是否命中缓冲。

索引治理：

```sql
-- 未使用索引（PG 提供）
SELECT schemaname, relname, indexrelname, idx_scan
FROM pg_stat_user_indexes
WHERE idx_scan = 0 AND indexrelname NOT LIKE '%_pkey';

-- 索引大小
SELECT pg_size_pretty(pg_relation_size('idx_users_age'));

-- 删除冗余
DROP INDEX IF EXISTS idx_users_age;
```

## 十、与 MySQL 索引对比

| 维度 | PostgreSQL | MySQL (InnoDB) |
| --- | --- | --- |
| 默认 | B-tree | B+tree（聚簇） |
| 多值/JSON 索引 | GIN | 生成列 + 索引（弱） |
| 空间/几何 | GiST + PostGIS | 空间类型（弱） |
| 部分索引 | ✅ | ❌（需前缀过滤变通） |
| 表达式索引 | ✅ | ❌（需虚拟列） |
| 覆盖索引 | INCLUDE | 索引即数据（聚簇天然覆盖） |
| 轻量大表索引 | BRIN | ❌ |
