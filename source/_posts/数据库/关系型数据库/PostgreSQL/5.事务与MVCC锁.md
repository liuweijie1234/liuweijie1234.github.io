# PostgreSQL 事务与 MVCC / 锁

PostgreSQL 以**严格遵循 SQL 标准的事务与隔离级别**闻名，其 MVCC 实现与 MySQL（undo 日志）思路不同——它靠**行多版本 + 事务 ID + VACUUM** 实现并发。本文深入 ACID、MVCC 原理、四种隔离级别、锁体系与死锁处理。

## 一、事务基础

```sql
BEGIN;                       -- 或 START TRANSACTION
UPDATE accounts SET bal = bal - 100 WHERE id = 1;
UPDATE accounts SET bal = bal + 100 WHERE id = 2;
COMMIT;                      -- 提交
-- ROLLBACK;                 -- 回滚
```

- 默认**自动提交（autocommit）**：每条语句即一个事务。
- 支持 `SAVEPOINT` 部分回滚：

```sql
BEGIN;
INSERT ...;
SAVEPOINT sp1;
UPDATE ...;          -- 若失败
ROLLBACK TO sp1;     -- 回退到保存点
COMMIT;
```

## 二、ACID

| 属性 | Postgres 实现 |
| --- | --- |
| 原子性 | 事务全成功或全回滚 |
| 一致性 | 约束（PK/FK/CHECK/触发器）保证 |
| 隔离性 | MVCC + 锁 |
| 持久性 | WAL 落盘（`synchronous_commit`） |

## 三、MVCC 原理（核心）

Postgres 每行（tuple）带事务可见性信息：

- `xmin`：插入该行的事务 ID。
- `xmax`：删除/更新（旧版本）的事务 ID；更新 = 旧版本标 `xmax` + 新版本插入。
- 事务通过自身的 **快照（snapshot = 当前活跃事务列表）** 判断某版本对自己是否可见：
  - `xmin` 已提交且不在活跃列表 → 可见起点。
  - `xmax` 未提交或为 0 → 未被删除。
- 旧版本（死元组）对其它事务不再可见后，由 **VACUUM** 回收（见 第 2 章）。

> 与 MySQL 对比：MySQL InnoDB 用 **undo 日志** 构建旧版本（原地更新 + 回滚指针），Postgres 用 **行多版本**（原地追加新版本）。两者都能实现非锁定读，但 Postgres 需额外 VACUUM 治理膨胀。

## 四、隔离级别

SQL 标准四级，Postgres 全部支持（且**真正实现了 SERIALIZABLE**，不像 MySQL 用间隙锁变通）：

| 级别 | 脏读 | 不可重复读 | 幻读 | 说明 |
| --- | --- | --- | --- | --- |
| READ UNCOMMITTED | ❌避免 | — | — | PG 中实际等同于 READ COMMITTED |
| READ COMMITTED（默认） | ✅无 | 可能 | 可能 | 语句级快照 |
| REPEATABLE READ | ✅无 | ✅无 | ✅无（靠 SI） | 事务级快照 |
| SERIALIZABLE | ✅无 | ✅无 | ✅无 | 真串行化（SSI 可串行化快照隔离） |

```sql
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;
BEGIN; ... COMMIT;
```

- **READ COMMITTED**：每条语句看到已提交的最新数据。
- **REPEATABLE READ**：整个事务用同一快照，可重复读；PG 用快照隔离天然防幻读。
- **SERIALIZABLE**：通过 SSI（Serializable Snapshot Isolation）检测写偏斜（write skew），冲突时抛 `serialization_failure`，需应用重试。

## 五、锁体系

Postgres 锁分多层：

### 5.1 表级锁

`SELECT` 默认加 `ACCESS SHARE`；`UPDATE/DELETE/INSERT` 加 `ROW EXCLUSIVE`；`ALTER TABLE` 加 `ACCESS EXCLUSIVE`（阻塞一切）。多数 DML 互不阻塞（行级锁细化），但 DDL 会阻塞读写。

### 5.2 行级锁

- `FOR UPDATE`：锁选定行，阻止其它事务修改/加同锁。
- `FOR SHARE`：共享行锁，阻止修改但允许 `FOR SHARE`。
- 由 MVCC 提供「读不阻塞写、写不阻塞读」——普通 SELECT 不加锁（快照读）。

```sql
BEGIN;
SELECT * FROM accounts WHERE id=1 FOR UPDATE;  -- 悲观锁
UPDATE accounts SET bal=bal-100 WHERE id=1;
COMMIT;
```

### 5.3 意向锁（Intention Locks）

表级意向锁协调表锁与行锁，避免逐行检查。

### 5.4 咨询锁（Advisory Lock）

应用层自定义的轻量锁，用「键」协调，适合分布式调度防重：

```sql
SELECT pg_advisory_xact_lock(12345);  -- 事务级咨询锁
```

## 六、死锁

两个事务互相等待对方持有的锁 → 死锁。PG 会**自动检测**并回滚其中一个（抛 `deadlock detected`），应用应捕获重试。

预防：所有事务**按固定顺序**访问资源、缩短事务、避免长事务持锁。

## 七、乐观并发控制（乐观锁）

Postgres 没有 MySQL 那样的 `version` 字段乐观锁语法，但可用 `xmin`/`ctid` 或显式版本列实现：

```sql
-- 应用层携带读取时的 xmin，提交时校验未被改
UPDATE accounts SET bal=200, version=version+1
WHERE id=1 AND version=5;   -- 影响行数 0 即被并发修改
```

## 八、与 MySQL 对比

| 维度 | PostgreSQL | MySQL (InnoDB) |
| --- | --- | --- |
| MVCC 实现 | 行多版本 + VACUUM | undo 日志 + 回滚指针 |
| SERIALIZABLE | ✅ 真串行化（SSI） | ⚠️ 间隙锁近似 |
| 默认隔离 | READ COMMITTED | REPEATABLE READ |
| 读阻塞写 | ❌ 快照读不阻塞 | ❌ 一致读不阻塞 |
| 死锁处理 | 自动检测回滚一方 | 自动检测回滚一方 |
| 长事务代价 | 表膨胀（VACUUM 压力） | undo 增长 |
