# PostgreSQL 查询优化与执行计划

Postgres 拥有成熟基于代价的优化器（Cost-Based Optimizer）。理解 `EXPLAIN`、统计信息、连接策略与常见优化手段，是写出高效 SQL 的关键。本文系统讲解。

## 一、EXPLAIN：看清执行计划

```sql
EXPLAIN SELECT * FROM users WHERE city='北京' AND age>18;

-- 实际执行 + 资源统计（最重要）
EXPLAIN (ANALYZE, BUFFERS, VERBOSE)
SELECT * FROM users WHERE city='北京';
```

输出是**计划树**，从内到外、从下到上执行：

```
Aggregate
  ->  Hash Join
        ->  Seq Scan on orders
        ->  Hash
              ->  Index Scan using pk_users on users
```

### 关键节点

| 节点 | 含义 |
| --- | --- |
| `Seq Scan` | 全表扫描，大表危险 |
| `Index Scan` | 走索引并回表 |
| `Index Only Scan` | 覆盖索引，不回表（最优） |
| `Bitmap Heap Scan` | 位图定位后回表 |
| `Hash Join` | 小表建哈希，大表探测 |
| `Nested Loop` | 外表每行驱动内表（适合索引内表） |
| `Merge Join` | 两表均已排序，归并（适合大表） |
| `Sort` | 排序（内存不足落盘慢） |
| `Gather` | 并行收集（Parallel 前缀表示并行 worker） |

### ANALYZE 与 BUFFERS 解读

- `actual time=0.02..0.05 rows=10`：实际耗时与行数。
- `Buffers: shared hit=5 read=20`：缓冲命中/磁盘读；`read` 多说明未进缓存。
- `Planning Time` / `Execution Time`：计划耗时 / 执行耗时。
- **计划行数 vs 实际行数偏差大** → 统计信息不准，需 `ANALYZE`。

## 二、统计信息与代价模型

优化器靠 `pg_statistic`（由 `ANALYZE` 收集）估算行数，再算每种路径的「代价（cost）」选最小。

```sql
-- 更新统计（自动 autovacuum 会做，但大变后手动）
ANALYZE users;
ANALYZE VERBOSE;

-- 关键配置
default_statistics_target = 100   -- 调大提升估算精度（列级可设）
```

> 常见坑：刚灌入大量数据未 `ANALYZE`，优化器误判走 Seq Scan。建完索引/导完数据务必 `ANALYZE`。

## 三、连接（JOIN）策略

Postgres 三种物理连接：

| 策略 | 适用 |
| --- | --- |
| Nested Loop | 内表有索引、外表小 |
| Hash Join | 无索引、两表较大（小表进内存哈希） |
| Merge Join | 两表已按连接键排序 |

优化器据统计选最优；可用 `SET enable_hashjoin=off` 临时验证哪种更优（诊断用）。

## 四、常见优化手段

### 4.1 索引驱动

- 为 `WHERE` / `JOIN` / `ORDER BY` 列建合适索引（B-tree/GIN/部分/表达式）。
- 复合索引遵循最左前缀。
- 大表时间列用 BRIN（见 第 4 章）。

### 4.2 避免索引失效

```sql
-- 对列用函数 → 索引失效
WHERE lower(email)='a@b.com'        -- 需表达式索引 lower(email)
-- 类型不匹配
WHERE id = '123'                    -- id 是 int，隐式转换可能不走索引
-- 前导模糊
WHERE name LIKE '%明'               -- 不走（后缀/中缀需 pg_trgm + GIN）
-- 否定
WHERE status <> 'A'                 -- 选择性差，常走全扫
```

### 4.3 只取所需列（覆盖索引）

```sql
-- 用 INCLUDE 建覆盖索引，触发 Index Only Scan
CREATE INDEX idx_city_cover ON users(city) INCLUDE(name, age);
```

### 4.4 分页优化

```sql
-- 深分页慢
SELECT * FROM orders ORDER BY id LIMIT 10 OFFSET 100000;

-- 游标/Keyset 分页（快）
SELECT * FROM orders WHERE id > 100000 ORDER BY id LIMIT 10;
```

### 4.5 CTE 与子查询

PG 12+ 中 CTE（`WITH`）默认**内联**（不再总是物化），多次引用才物化。复杂场景可用 `MATERIALIZED` 显式控制：

```sql
WITH t AS MATERIALIZED (SELECT ... FROM big) SELECT ...
```

### 4.6 并行查询

大表聚合可并行（`max_parallel_workers_per_gather`）。`Gather` 节点表示并行收集结果。

## 五、慢查询定位

```sql
-- 开启 SQL 统计扩展
CREATE EXTENSION pg_stat_statements;

-- 查最耗时/最多调用的 SQL
SELECT query, calls, total_exec_time, mean_exec_time
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 10;
```

配合 `log_min_duration_statement = 1000`（记录 >1s 的 SQL）到日志。

## 六、与 MySQL EXPLAIN 对比

| 维度 | PostgreSQL | MySQL |
| --- | --- | --- |
| 输出 | 文本计划树 | 表格（select_type/type/key/rows） |
| 实际执行 | `EXPLAIN ANALYZE`（真跑） | `EXPLAIN ANALYZE`（也真跑） |
| 代价显示 | `cost=0.00..35.50` | 无 cost 概念 |
| 统计 | `pg_statistic` + `ANALYZE` | `innodb_index_stats` + `ANALYZE TABLE` |
| 并行 | `Parallel/Gather` 节点清晰 | 有但展示弱 |
