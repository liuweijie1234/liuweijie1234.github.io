# PostgreSQL 与 MySQL 对比选型

PostgreSQL 与 MySQL 是开源关系库双雄，但**设计哲学不同**：MySQL 追求「简单、快、易上手」，Postgres 追求「标准、严谨、可扩展」。选型应基于团队、业务与功能需求。本文系统对照两者。

## 一、核心差异速查

| 维度 | PostgreSQL | MySQL (InnoDB) |
| --- | --- | --- |
| 定位 | 对象关系型 / 严谨标准 | 轻量关系型 / 易用高性能 |
| 许可证 | PostgreSQL License（宽松，可闭源商用） | GPL（派生需开源，或用商业版） |
| 进程模型 | 多进程（每连接一进程） | 单进程多线程 |
| 存储 | 统一 Heap（无插件式引擎） | 插件式（InnoDB 主导） |
| 默认隔离 | READ COMMITTED | REPEATABLE READ |
| MVCC | 行多版本 + VACUUM | undo 日志 + 回滚指针 |
| SERIALIZABLE | ✅ 真串行化（SSI） | ⚠️ 间隙锁近似 |
| JSON | ✅ jsonb（强，GIN 索引） | ✅ JSON（生成列变通） |
| 数组/范围 | ✅ 原生 | ❌ |
| 全文检索 | ✅ 内置（tsvector） | 弱（仅 MyISAM 旧 FULLTEXT） |
| 索引类型 | B-tree/GIN/GiST/BRIN/Hash/SP-GiST | B+tree / 全文 / 空间（R-tree） |
| 部分/表达式索引 | ✅ 原生 | 需虚拟列 |
| 地理空间 | ✅ PostGIS（业界标准） | ❌（弱） |
| 复制 | 流复制 / 逻辑发布订阅 | binlog 主从 / 组复制 MGR |
| 视图/存储过程 | ✅ 成熟（PL/pgSQL） | ✅（早期弱，8.0 增强） |
| 窗口函数 | ✅ 早且全 | ✅ 8.0 起 |
| 读写性能 | 复杂查询强、并发写稳定 | 简单读写/高并发读极快 |
| 运维复杂度 | 中高（VACUUM/参数多） | 低（开箱即用） |

## 二、什么时候选 PostgreSQL

1. **复杂 SQL / 报表分析**：窗口函数、CTE、复杂 join，优化器成熟严谨。
2. **需要 JSON + 关系混合**：同一库既存结构化又存半结构化（jsonb + GIN）。
3. **地理空间（GIS）**：PostGIS 是事实标准。
4. **强一致 / 严格标准**：真 SERIALIZABLE、严格类型与约束。
5. **可扩展性需求**：自定义类型、函数、FDW 外部表、扩展生态。
6. **不愿被 GPL 束缚 / 闭源分发**：更友好的许可证。

## 三、什么时候选 MySQL

1. **高并发简单读写、Web 业务**：如电商、CMS，吞吐极高、运维简单。
2. **团队熟悉 MySQL / 生态成熟**：招聘、工具、云托管成本低。
3. **读写分离、分库分表**：中间件（ShardingSphere）生态完善。
4. **快速上手、低运维负担**：默认配置即用，VACUUM 之类概念少。

## 四、性能认知纠偏

- 「MySQL 比 PG 快」是过时印象。现代 PG 在复杂查询、并行执行上很强；MySQL 在极简 KV 式查询、高并发连接读上仍有优势。
- PG 的**多进程**在高连接数时内存开销大，需 PgBouncer 连接池（类似 Redis 思路）。
- 两者都能支撑大型互联网业务，性能瓶颈多在**索引/SQL 写法/架构**，而非引擎本身。

## 五、迁移注意

- 方言差异：MySQL 的 `AUTO_INCREMENT` ↔ PG 的 `SERIAL`/`IDENTITY`；反引号 `` ` `` ↔ 双引号 `"`；`LIMIT a,b` ↔ `LIMIT b OFFSET a`。
- 类型映射：`DATETIME` ↔ `TIMESTAMP`/`TIMESTAMPTZ`；`TINYINT(1)` ↔ `BOOLEAN`；`TEXT` 通用。
- 函数差异：`IF()`/`NOW()` 部分需改写；PG 用 `COALESCE`、`now()`。
- 工具：`pgloader`（MySQL→PG 迁移利器）、`AWS DMS`、`Debezium`（CDC）。

## 六、混合架构

现实常是「多库并存」：

```
PostgreSQL  ── 复杂业务/分析/GIS/JSON 混合
MySQL       ── 高并发交易/读写分离核心
Redis       ── 缓存/会话/锁
MongoDB     ── 灵活半结构化文档
```

> 选型不是「二选一」，而是「按访问模式分而治之」。详见 [10.MongoDB 与关系型对比](../../文档型数据库/MongoDB/10.与关系型数据库对比.md)。

## 七、总结

> **追求严谨、扩展、复杂查询与标准兼容 → PostgreSQL；追求简单、高并发读写、快速落地 → MySQL。** 两者都是世界级开源数据库，理解差异才能正确选型。
