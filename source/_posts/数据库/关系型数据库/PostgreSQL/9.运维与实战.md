# PostgreSQL 运维与实战

Postgres 运维的核心是**管好 VACUUM、监控统计、备份恢复与连接池**。本文汇总日常运维命令、参数调优、备份策略、监控体系与典型实战问题。

## 一、关键配置文件

| 文件 | 作用 |
| --- | --- |
| `postgresql.conf` | 主配置（内存、连接、WAL、日志） |
| `pg_hba.conf` | 客户端认证控制 |
| `pg_ident.conf` | 系统用户↔角色映射 |

热重载：

```sql
SELECT pg_reload_conf();     -- 不重启生效（多数参数）
-- 或系统命令：systemctl reload postgresql
```

## 二、内存与性能参数

```ini
shared_buffers = 4GB          # 建议 RAM 的 25%
effective_cache_size = 12GB   # 告诉优化器 OS 页缓存大小（非分配）
work_mem = 64MB               # 每排序/哈希操作私有内存（×并发，慎增）
maintenance_work_mem = 1GB   # VACUUM/建索引
max_connections = 200         # 高并发配 PgBouncer，不必调太大
wal_level = replica
checkpoint_timeout = 5min
max_wal_size = 2GB
random_page_cost = 1.1        # SSD 下调，让优化器更倾向索引
```

> `work_mem` 是**每个操作**的内存，并发排序多时总和可能很大，盲目调大会 OOM。连接池 + 合理 `work_mem` 是关键。

## 三、VACUUM 与表膨胀治理

MVCC 产生死元组，必须靠 VACUUM 回收（见 第 2 章）：

```sql
-- 查看膨胀
SELECT schemaname, relname, n_dead_tup, n_live_tup,
       round(n_dead_tup::numeric/nullif(n_live_tup,0)*100,1) AS dead_pct
FROM pg_stat_user_tables
ORDER BY dead_pct DESC NULLS LAST
LIMIT 10;

-- 手动 vacuum + 统计
VACUUM (VERBOSE, ANALYZE) big_table;

-- autovacuum 关键参数
autovacuum = on
autovacuum_vacuum_scale_factor = 0.2   # 死元组占比触发阈值（大表可调小）
autovacuum_vacuum_cost_limit = 2000    # 控制 IO 占用
```

高频更新大表建议**单独调低阈值**，避免膨胀失控。

## 四、备份与恢复

### 4.1 逻辑备份（pg_dump / pg_dumpall）

```bash
# 单库
pg_dump -h localhost -U admin shop > shop.sql
# 压缩
pg_dump -Fc shop > shop.dump      # 自定义格式，可选择性恢复
# 恢复
pg_restore -d shop shop.dump

# 全实例
pg_dumpall > all.sql
```

### 4.2 物理备份 + PITR

```bash
# 基础备份
pg_basebackup -h primary -U replicator -D /backup/$(date +%F) -P -R
```

配合 WAL 归档（`archive_mode=on`）实现**时间点恢复**：

```ini
restore_command = 'cp /archive/%f %p'
recovery_target_time = '2026-07-30 14:00:00'
```

## 五、监控体系

### 5.1 内置统计视图

| 视图 | 用途 |
| --- | --- |
| `pg_stat_activity` | 当前连接/正在执行的 SQL、等待状态 |
| `pg_stat_user_tables` | 表级增删改查计数、死元组 |
| `pg_stat_user_indexes` | 索引使用次数（找冗余索引） |
| `pg_stat_statements` | SQL 级耗时/调用（需扩展） |
| `pg_stat_replication` | 主从复制延迟（`write_lag`/`flush_lag`） |

```sql
-- 查慢/锁等待
SELECT pid, state, wait_event_type, query
FROM pg_stat_activity
WHERE state <> 'idle' ORDER BY query_start;

-- 终止异常连接
SELECT pg_terminate_backend(pid) FROM pg_stat_activity
WHERE state='active' AND query_start < now() - interval '5 min';

-- 查复制延迟
SELECT * FROM pg_stat_replication;
```

### 5.2 外部监控

- **pgAdmin / PgBouncer 自带统计**。
- **Prometheus + Grafana**：`postgres_exporter` 采集。
- **pg_stat_statements**：最耗 SQL TOP N。
- **日志**：`log_min_duration_statement=1000` 记录慢 SQL，`log_lock_waits=on` 记录锁等待。

## 六、连接池：PgBouncer

Postgres 每连接一进程，高并发连接数大时开销高，务必用连接池：

```ini
# pgbouncer.ini
[databases]
shop = host=127.0.0.1 port=5432 dbname=shop

[pgbouncer]
pool_mode = transaction      # 事务级复用，最常用
max_client_conn = 1000
default_pool_size = 20
```

应用连 PgBouncer（如 6432 端口）而非直接连 PG。

## 七、典型实战问题

| 问题 | 现象 / 原因 | 解决 |
| --- | --- | --- |
| 表膨胀 | 死元组堆积，查询变慢 | 调 autovacuum、手动 VACUUM ANALYZE |
| 事务 ID 回卷（wraparound） | xid 接近 20 亿，库只读告警 | 紧急 VACUUM FREEZE，长期调 autovacuum |
| 连接数爆满 | `too many connections` | PgBouncer、调 `max_connections` |
| 慢查询 | 缺索引/统计过期 | 建索引、ANALYZE、EXPLAIN 调优 |
| 复制延迟 | 备机落后、大事务 | 拆小事务、提升备机 IO |
| 锁等待 | 长事务持锁阻塞 | 查 `pg_stat_activity`、pg_terminate_backend |
| 磁盘满 | WAL/归档堆积 | 清理归档、扩盘、调 `max_wal_size` |

## 八、与 MySQL 运维对比

| 维度 | PostgreSQL | MySQL |
| --- | --- | --- |
| 膨胀治理 | VACUUM（必须关注） | undo 自动回收 |
| 连接模型 | 每连接一进程 → 需连接池 | 多线程 → 原生高并发 |
| 备份 | pg_dump / pg_basebackup / PITR | mysqldump / XtraBackup |
| 慢 SQL | pg_stat_statements | slow query log / Performance Schema |
| 在线升级 | 逻辑复制跨版本 | 需兼容版本/主从切换 |
| 参数复杂度 | 中高 | 低 |
