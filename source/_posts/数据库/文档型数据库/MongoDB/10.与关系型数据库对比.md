# MongoDB 与关系型数据库对比

理解 MongoDB 与 MySQL/PostgreSQL 等关系型数据库的差异，是正确选型的前提。本文从数据模型、Schema、查询、事务、扩展、一致性六个维度系统对照，并给出「谁更适合」的结论。

## 一、概念映射

| 关系型（MySQL） | MongoDB | 说明 |
| --- | --- | --- |
| Database | Database | 同名概念 |
| Table | Collection | 集合无强制列 |
| Row | Document | 文档是 JSON 对象 |
| Column | Field | 字段可动态 |
| Index | Index | 概念一致（B-tree 为主） |
| JOIN | 内嵌 / `$lookup` | 优先内嵌建模 |
| 主键（PK） | `_id` | 默认 ObjectId |
| 外键（FK） | 引用 `_id` | 无级联约束 |
| 事务 | 多文档事务（4.0+） | 单文档天然原子 |
| SQL | MQL | 声明式 vs 文档式 |
| 存储过程 | 聚合/JS（受限） | — |

## 二、六维对照

### 2.1 数据模型

- **关系型**：二维表，行+列，强类型，表间外键约束。
- **MongoDB**：嵌套文档，字段可缺省/异质，用内嵌表达「一对少」，用引用表达「多对多」。

> 对象到存储的映射：关系型要拆多表 + join；Mongo 往往一个文档搞定。ORM 成本更低。

### 2.2 Schema 灵活性

- **关系型**：先 DDL 建表、定列定类型，改结构需迁移（`ALTER`）。
- **MongoDB**：读时模式（Schema-on-Read），字段随文档而变，加字段零成本。

### 2.3 查询语言

- **关系型**：SQL 表达力强，join/子查询/窗口函数成熟，优化器智能。
- **MongoDB**：MQL 基于文档，CRUD 直观；聚合管道（Pipeline）强大但学习曲线陡；`$lookup` 类 join 但弱于 SQL。

### 2.4 事务与一致性

| 维度 | MySQL/PostgreSQL | MongoDB |
| --- | --- | --- |
| 单记录原子 | ✅ | ✅（单文档） |
| 多文档事务 | ✅ 原生、成熟 | 4.0+ 支持，有开销，官方建议少用 |
| 隔离级别 | RR/RC/SERIALIZABLE | snapshot |
| 默认一致性 | 通常强一致 | 最终一致（从节点读） |
| 外键约束 | ✅ 级联 | ❌ 应用层维护 |

### 2.5 扩展能力

| 维度 | 关系型 | MongoDB |
| --- | --- | --- |
| 垂直扩展 | ✅（加机器配置） | ✅ |
| 读扩展 | ✅（主从复制） | ✅（复制集从节点读） |
| 写/存储水平扩展 | 难（需分库分表中间件） | ✅（原生分片 Sharding） |
| 分布式事务 | 复杂（XA/中间件） | 4.2+ 跨分片事务 |

> MongoDB 的分片是**内建**能力，而关系库做水平拆分往往要引入 ShardingSphere 等中间件，改造成本高。

### 2.6 性能特征

- **关系型**：复杂关联、强事务、报表分析性能与稳定性更优，优化器成熟。
- **MongoDB**：简单 KV / 嵌套对象读写、水平扩展写入吞吐更优；但 join 重查询弱。

## 三、谁更适合（速查表）

| 场景 | 选 MongoDB | 选 MySQL/PostgreSQL |
| --- | --- | --- |
| 灵活/多变 schema | ✅ | |
| 高写入 + 水平扩展 | ✅（分片） | |
| 嵌套对象、一次取全 | ✅ | |
| 强事务、账务核心 | | ✅ |
| 复杂 join、报表分析 | | ✅ |
| 严格约束、规范化数据 | | ✅ |
| 地理/全文检索 | ✅（原生索引） | 需插件/外部 |

## 四、混合架构实践

生产系统常见「多库并存」：

```
┌────────────┐   ┌────────────┐   ┌──────────┐
│ PostgreSQL │   │  MongoDB   │   │  Redis   │
│ 核心交易/  │   | 业务灵活/ │   │ 缓存/    │
│ 账务/约束  │   | 半结构/   │   │ 会话/锁  │
│            │   | 海量文档  │   │          │
└────────────┘   └────────────┘   └──────────┘
```

- 用**关系库**保证核心数据的强一致与约束；
- 用 **MongoDB** 承接灵活、易变、需水平扩展的业务数据；
- 用 **Redis** 扛热点读与缓存。

## 五、迁移注意

从关系库迁 Mongo 时：

1. **反范式化**：把「一对少 / 生命周期一致」的表合并内嵌为文档。
2. **放弃外键**：用 `_id` 引用 + 应用层一致性保障。
3. **事务下沉**：能用单文档原子/内嵌解决的，绝不引入多文档事务。
4. **索引重建**：SQL 的复合索引经验可迁移，但注意 Mongo 的 ESR 与覆盖查询机制。
5. **工具**：`mongoshake`、`mongoimport`、各类 ETL 可辅助迁移。

## 六、总结

> MongoDB 不是关系库的「替代品」，而是**互补品**。它赢了灵活建模与水平扩展，输了强事务与复杂关联。选型应基于**访问模式与一致性需求**，而非「流行度」。
