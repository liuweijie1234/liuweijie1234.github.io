# MongoDB 数据模型与 BSON / 文档设计

灵活的文档模型是 MongoDB 的立身之本。但「灵活」不等于「随意」——优秀的文档设计能带来数量级的性能差异。本文深入 BSON 编码、文档结构、嵌入式 vs 引用的建模权衡，以及反范式设计的工程实践。

## 一、BSON：不只是 JSON

MongoDB 在磁盘和内存中存储的是 **BSON（Binary JSON）**，一种二进制序列化格式。相比 JSON，BSON：

- **类型更丰富**：支持 `Date`、`BinData`（二进制）、`ObjectId`、`Decimal128`、`Timestamp`、`Regex` 等。
- **带长度前缀**：每个元素记录类型 + 字段名 + 值，解析无需完整解析即可跳过。
- **有序字段**：文档内字段顺序保留（插入顺序），对覆盖索引等特性很重要。
- **空间换速度**：数字统一按 int32/int64/double 存储，遍历无需字符串解析。

### 主要 BSON 类型

| 类型 | 说明 | 示例 |
| --- | --- | --- |
| ObjectId | 12 字节唯一 ID（`_id` 默认类型） | `ObjectId("65f1c2...")` |
| String | UTF-8 编码 | `"hello"` |
| Int32 / Int64 | 整型 | `42` |
| Double | 浮点（默认数字类型） | `3.14` |
| Decimal128 | 高精度十进制，金融场景 | `Decimal128("9.99")` |
| Boolean | 布尔 | `true` |
| Date | 64 位毫秒时间戳 | `ISODate("2026-07-30")` |
| Array | 有序数组 | `["a","b"]` |
| Object | 嵌套子文档 | `{k: v}` |
| Null | 空值 | `null` |
| BinData | 二进制（图片/文件片段） | `BinData(0,...)` |
| Timestamp | 内部时间戳（用于 oplog） | `Timestamp(...)` |

### ObjectId 结构（12 字节）

```
| 4 字节时间戳 | 3 字节机器标识 | 2 字节进程号 | 3 字节计数器 |
```

- 前 4 字节是秒级时间戳，因此 `_id` 天然大致有序，插入性能友好。
- 注意：**ObjectId 的「时间」不可作为业务时间排序的强依据**（仅秒级、且受机器时钟影响）。业务时间请用独立的 `createdAt: Date` 字段并建索引。

## 二、文档（Document）基本结构

```javascript
{
  _id: ObjectId("65f1c2..."),
  title: "MongoDB 实战",
  price: 99.0,
  inStock: true,
  tags: ["数据库", "NoSQL"],
  author: { name: "张三", email: "z@a.com" },  // 嵌套子文档
  chapters: [                                  // 嵌套数组
    { no: 1, name: "入门" },
    { no: 2, name: "索引" }
  ],
  createdAt: ISODate("2026-07-30T00:00:00Z")
}
```

### 字段命名约束

- `_id` 是保留的主键字段，必须为集合内唯一；若插入不指定，驱动自动生成 ObjectId。
- 字段名不能包含 `\0`（空字符）。
- 字段名以 `$` 开头或含 `.` 在查询上下文有特殊含义，**建模时避免**用作普通字段名（点表示嵌套路径）。
- 单文档上限 **16 MB**（设计层约束，防止单文档过大）。

## 三、建模核心决策：嵌入（Embed）还是引用（Reference）

这是 MongoDB 建模最重要的权衡，对应关系库的「范式 vs 反范式」。

### 方案 A：内嵌（Embedded / 反范式）

把相关数据作为一个子文档或数组放进同一文档。

```javascript
// 博客文章 + 评论内嵌
{
  _id: ...,
  title: "MongoDB 建模",
  comments: [
    { user: "A", text: "好文", at: ISODate(...) },
    { user: "B", text: "收藏", at: ISODate(...) }
  ]
}
```

**适用场景**：一对少 / 一对多且「多」端数据量可控、生命周期一致、一起读取。
**优点**：一次查询、一次 IO、原子更新、无 join。
**缺点**：文档膨胀（接近 16MB 上限时不可行）、数组过大导致写放大。

### 方案 B：引用（Reference / 范式）

用 `_id` 互相关联，类似外键。

```javascript
// 文章
{ _id: post1, title: "MongoDB 建模" }
// 评论（独立集合）
{ _id: ..., postId: post1, user: "A", text: "好文" }
```

**适用场景**：一对多且「多」端数据巨大（如百万级评论）、需独立查询/分页、生命周期独立。
**优点**：文档小、可独立扩展、避免写放大。
**缺点**：需 `$lookup`（类 join）或多轮查询，跨文档无事务一致性（同分片内 4.2+ 可事务）。

### 决策清单

| 维度 | 倾向内嵌 | 倾向引用 |
| --- | --- | --- |
| 关系基数 | 一对一、一对少 | 一对多（多端巨大）、多对多 |
| 读取模式 | 总是一起读 | 单独读「多」端 |
| 写频率 | 「多」端 seldom 写 | 「多」端高频写 |
| 数据量 | 整体 < 几 KB | 「多」端可能无限增长 |
| 一致性 | 需要原子更新整体 | 可容忍最终一致 |

> 经验法则：**优先内嵌，遇到「无限增长数组」或「多对多」再拆引用**。MongoDB 的强项就是反范式内嵌。

## 四、多态（Polymorphic）建模

同一集合存不同类型文档，用 `type` 字段区分——非常适合「活动流」、「商品多规格」等场景：

```javascript
// 同一 events 集合存多种事件
{ _id, type: "login",    uid: 1, at: ... }
{ _id, type: "purchase", uid: 1, sku: "x", amount: 99, at: ... }
```

查询时按 `type` 建索引即可高效分离。

## 五、常用的模式设计（Patterns）

MongoDB 官方提出一系列「模式设计模式」，解决典型反范式难题：

### 5.1 属性模式（Attribute / Extended Reference）
将「名称-值」对数组化，适合字段稀疏、差异大的场景（如商品属性）：

```javascript
{
  name: "iPhone",
  attrs: [
    { k: "颜色", v: "钛金" },
    { k: "容量", v: "256G" }
  ]
}
```

### 5.2 分桶模式（Bucket）
把时间序列数据按时间窗口聚合进一个文档，减少文档数、提升扫描效率：

```javascript
{
  sensorId: "s1",
  bucketStart: ISODate("2026-07-30T00:00:00Z"),
  readings: [ { t: ..., v: 23.1 }, { t: ..., v: 23.4 }, ... ]  // 1 分钟一条
}
```

### 5.3 子集模式（Subset）
对「大文档 + 频繁读小字段」场景，把热点字段拆到单独小集合，避免每次拉大文档。

### 5.4 计算模式（Computed）
把需要复杂聚合的结果预计算并存储，读时直接取，用定时任务/触发器维护。

## 六、与关系型建模对比示例

关系库「订单-订单项」：

```sql
orders(order_id, user_id, ...)
order_items(item_id, order_id, sku, qty, price)
```

MongoDB 反范式内嵌（订单不常改、订单项随订单读）：

```javascript
{
  _id: order1,
  userId: 1,
  status: "PAID",
  items: [
    { sku: "x", qty: 2, price: 99 },
    { sku: "y", qty: 1, price: 199 }
  ],
  total: 397,
  createdAt: ISODate(...)
}
```

> 若订单项需要独立库存扣减、单独退款，则拆成引用更合适。建模永远服务于**访问模式**。

## 七、设计检查清单

1. 文档是否遵循「一次查询即可满足主路径」？
2. 是否有数组会无限增长（>几百元素）？有则拆引用。
3. 16MB 上限是否可能触达？
4. 高频更新字段是否集中，避免大文档写放大？
5. 是否需要跨文档事务？能避免最好（分布式事务有成本）。
