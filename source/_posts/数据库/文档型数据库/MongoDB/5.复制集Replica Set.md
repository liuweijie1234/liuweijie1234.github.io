# MongoDB 复制集 Replica Set

复制集（Replica Set）是 MongoDB 实现**高可用与数据冗余**的核心机制：一组 `mongod` 实例维护相同数据集，自动选主、故障转移。本文讲清架构、oplog 同步原理、选举与读写配置。

## 一、架构概览

一个复制集通常包含：

- **Primary（主节点）**：唯一可接受写请求的节点，把所有写操作记录到 **oplog**。
- **Secondary（从节点）**：异步复制 oplog 并重放，保持与主一致；可接受读（配置后）。
- **Arbiter（仲裁节点，可选）**：只投票、不存数据，用最小资源参与选举（不建议生产大量使用）。

```
       写 ──▶ Primary
                │ oplog
                ▼
      ┌─────────┼─────────┐
    Sec1      Sec2      Arbiter
   (数据)    (数据)     (只投票)
```

> 推荐部署 **奇数个成员**（3/5/7）以避免选举平票。3 节点最常见：1 Primary + 2 Secondary。

## 二、oplog：复制的命脉

oplog（operation log）是**固定集合（capped collection）** `local.oplog.rs`，记录所有修改数据的幂等操作（插入、更新、删除）。Secondary 不断：

1. 向 Primary 拉取 oplog（long polling）。
2. 按时间戳顺序**重放**到自身数据。

```javascript
// 查看 oplog
use local
db.oplog.rs.find().sort({ $natural: -1 }).limit(3).pretty()

// oplog 条目示例
{
  ts: Timestamp(1690000000, 1),
  op: "i",                 // i=insert, u=update, d=delete, c=command
  ns: "shop.users",        // 命名空间
  o:  { _id: ..., name: "张三" }
}
```

> oplog 是**幂等**的（重放多次结果一致），因此网络重传安全。oplog 大小有限（默认约占磁盘 5%），写满后循环覆盖——若 Secondary 落后超过 oplog 窗口，会出现「oplog 失步」，需全量重新同步（resync）。

## 三、部署复制集

### 配置文件（每个节点）

```yaml
replication:
  replSetName: rs0
net:
  bindIp: <本机IP>
```

### 初始化

```javascript
// 在任一节点 mongosh 执行
rs.initiate({
  _id: "rs0",
  members: [
    { _id: 0, host: "192.168.1.10:27017" },
    { _id: 1, host: "192.168.1.11:27017" },
    { _id: 2, host: "192.168.1.12:27017", arbiterOnly: true }
  ]
})

rs.status()        // 查看状态
rs.isMaster()      // 谁是主
```

## 四、选举（Election）

- 主节点宕机或网络分区时，剩余节点发起选举。
- 节点需获得**多数（majority）** 选票才能成为 Primary。
- 优先级（`priority`）、数据新鲜度（oplog 最新时间戳）影响选举结果。
- 默认 10 秒内完成故障转移；`electionTimeoutMillis` 可调。

> **多数派原则**：3 节点容忍 1 台故障；5 节点容忍 2 台。若存活节点不足多数（如 3 节点挂 2 台），剩余节点降级为只读，**无法写入**——这是为防脑裂的代价。

## 五、读写配置

### 写关注 WriteConcern

控制写操作需确认多少个节点：

```javascript
// 写主即可返回（默认，快但可能丢）
db.users.insertOne({...}, { writeConcern: { w: 1 } })

// 写主 + 至少 1 个从节点确认（更强持久性）
db.users.insertOne({...}, { writeConcern: { w: 2, wtimeout: 5000 } })

// 多数派确认（最强，跨节点故障不丢）
{ w: "majority" }
```

### 读偏好 ReadPreference

```javascript
// 从从节点读（分担主压力，可能读到旧数据）
db.users.find().readPref("secondary")

// 可选：primary / primaryPreferred / secondary / secondaryPreferred / nearest
```

> 从节点读有**复制延迟**，读到旧数据是预期内的。强一致读必须走主节点。

## 六、延迟节点与节点标签

- **Hidden / Delayed 节点**：配置 `hidden:true`、`slaveDelay: 3600`，用于备份或误操作恢复（落后 1 小时的副本，可回滚「误删库」）。
- **节点标签（tags）**：按地域/用途路由读流量。

```javascript
// 路由到「报表」用节点
db.users.find().readPref("nearest", [], { tagSets: [{ usage: "report" }] })
```

## 七、典型运维

```javascript
rs.add("192.168.1.13:27017")        // 扩容
rs.remove("192.168.1.12:27017")     // 缩容
rs.stepDown(60)                     // 主主动让位（维护用）
rs.conf()                           // 当前配置
```

## 八、与分片的关系

复制集解决**高可用 + 读扩展**；分片（第 6 章）解决**写/存储水平扩展**。生产集群通常**每个分片本身就是一个复制集**——两者正交、组合使用。
