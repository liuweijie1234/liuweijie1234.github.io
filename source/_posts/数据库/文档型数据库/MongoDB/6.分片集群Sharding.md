# MongoDB 分片集群 Sharding

当数据量或写入吞吐超过单机上限，就需要**分片（Sharding）**：把数据按分片键（shard key）水平切分到多个分片（每个分片是一个复制集），实现存储与写入的线性扩展。本文讲清架构、分片键选型、均衡与避坑。

## 一、为什么需要分片

- 单机磁盘/内存有上限；索引无法全驻留 RAM，性能崩塌。
- 写入集中在单 Primary，成为瓶颈。
- 复制集只能「复制」不能「拆分」——读写扩展有限。

分片把数据集切成**块（chunk）** 分布到多个分片，写入与存储并行化。

## 二、集群三大角色

```
                 ┌─────────────┐
   应用 ───────▶ │  Mongos     │  (路由/查询分发，无状态，可多实例)
                 └──────┬──────┘
                        │
            ┌───────────┼────────────┐
            ▼           ▼            ▼
       Config Server  Shard1(rs)  Shard2(rs)  Shard3(rs)
       (元数据/集群   (复制集)     (复制集)     (复制集)
        配置, 通常3节点)
```

| 角色 | 作用 |
| --- | --- |
| **Mongos** | 查询路由器，解析请求、定位目标分片、聚合结果；应用只连它 |
| **Config Server** | 存储集群元数据（chunk 分布、shard 列表），建议 3 节点复制集 |
| **Shard** | 实际存数据，每个是一个复制集（高可用 + 分片双保险） |

## 三、分片键（Shard Key）—— 最重要的决策

分片键决定数据如何分布。选错会导致「热点分片」「无法扩展」。

### 3.1 分片键类型

- **哈希分片（Hashed）**：对分片键值做哈希，数据均匀分布，避免热点；但**范围查询低效**（分散到所有分片）。

  ```javascript
  sh.shardCollection("shop.orders", { _id: "hashed" })
  ```

- **范围分片（Ranged）**：按分片键值区间分布，范围查询高效；但易出现**热点**（如自增 `_id` 全写入最后一个分片）。

  ```javascript
  sh.shardCollection("shop.orders", { userId: 1 })
  ```

### 3.2 好的分片键特征

| 特征 | 说明 |
| --- | --- |
| 高基数（Cardinality） | 取值足够多，才能切出足够 chunk |
| 均匀分布 | 写入/读取分散到各分片，无单点热点 |
| 匹配查询模式 | 常用查询带分片键，可「定向路由」而非广播 |

> ⚠️ **自增 `_id` 作范围分片键是经典反例**：新数据永远落在最大 `_id` 的分片，写入热点集中。此类场景改用 **哈希分片** 或 **复合键（如 `{region:1, _id:"hashed"}`）**。

### 3.3 不可变更

分片键一旦选定**无法修改**（除非重建集合）。务必提前评估访问模式。

## 四、Chunk 与均衡（Balancer）

- 数据被切分为 **chunk**（默认 64MB），分布在各分片。
- **Balancer**（后台进程）监控各分片 chunk 数量，当差异超过阈值时迁移 chunk，保持均衡。
- 迁移期间对性能有影响，可在业务低峰开启（`activeWindow`）。

```javascript
sh.status()                       // 查看分片与 chunk 分布
sh.enableBalancing("shop.orders")
sh.disableBalancing("shop.orders")
sh.setBalancerState(true)
```

## 五、部署要点

1. 先部署 Config Server（3 节点复制集）。
2. 部署各 Shard（每个是复制集）。
3. 启动 Mongos，指定 config 地址。
4. 在 Mongos 上 `sh.addShard(...)` 添加分片。
5. 对数据库启用分片：`sh.enableSharding("shop")`。
6. 对集合指定分片键：`sh.shardCollection(...)`。

```javascript
sh.addShard("rs1/192.168.1.10:27017,192.168.1.11:27017")
sh.addShard("rs2/192.168.1.20:27017")
sh.enableSharding("shop")
sh.shardCollection("shop.orders", { userId: 1 })
```

## 六、查询路由

- 查询带分片键 → **定向（Targeted）** 路由到单一/少数分片，快。
- 查询无分片键 → **散布-聚集（Scatter-Gather）** 广播所有分片再合并，慢。

因此索引策略也要配合：分片键本身自动建索引，且应尽量让高频查询带分片键。

## 七、常见坑

| 问题 | 原因 / 解决 |
| --- | --- |
| 写入热点 | 范围分片键单调递增 → 改用哈希分片 |
| 无法删除分片键 | 设计期定好，否则重建集合 |
| 广播查询慢 | 查询缺分片键 → 调整查询或复合分片键 |
| chunk 无法分裂 | 分片键基数太低（如布尔字段）→ 选高基数字段 |
| 大文档 / 超大 chunk | 单 chunk 数据量异常，检查分片键分布 |

## 八、分片 vs 复制集 速查

| 能力 | 复制集 | 分片 |
| --- | --- | --- |
| 数据冗余/高可用 | ✅ | ✅（每个分片复制集） |
| 读扩展 | ✅（从节点读） | ✅ |
| 写扩展 | ❌（仅单主写） | ✅（多分片并行写） |
| 存储扩展 | ❌（受单机限制） | ✅ |
| 运维复杂度 | 低 | 高 |

> 经验：**先垂直优化（索引/内存/SSD），确认单机真到瓶颈再上分片**。分片运维成本显著更高。
