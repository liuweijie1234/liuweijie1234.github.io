# MongoDB 事务与一致性

MongoDB 早期只保证**单文档原子性**，多文档需靠应用层补偿。4.0 引入复制集多文档事务，4.2 支持跨分片分布式事务，正式补齐 ACID。本文讲清一致性模型、写关注、读关注、多文档事务与代价。

## 一、一致性与「关注」模型

MongoDB 用三个「关注（Concern）」维度精确控制一致性-可用性权衡：

### 1.1 WriteConcern（写确认级别）

| 值 | 含义 | 持久性 |
| --- | --- | --- |
| `w:0` | 不等待确认（fire and forget） | 最低 |
| `w:1` | 主节点写入即确认（默认） | 主挂可能丢 |
| `w:2` | 主 + 1 从确认 | 较高 |
| `w:"majority"` | 多数派落盘确认 | 强持久，推荐关键数据 |

```javascript
db.orders.insertOne({...}, { writeConcern: { w: "majority", j: true } })
// j:true 表示写进 oplog 的 journal（WAL）才算确认
```

### 1.2 ReadConcern（读一致性级别）

| 值 | 含义 |
| --- | --- |
| `local` | 读本地最新（可能未复制，可脏读） |
| `majority` | 只读取「多数派已确认」的数据，**防脏读** |
| `linearizable` | 线性一致，最强但最慢，适合关键读校验 |
| `available` | 分片场景，可能返回孤立文档 |

### 1.3 ReadPreference（读偏好）

决定从哪个节点读（`primary` / `secondary` / `nearest` 等），见第 5 章。

> **快照隔离**：`readConcern: "snapshot"` + `writeConcern: "majority"` 构成「可重复读」的快照，事务内多次读一致。

## 二、单文档原子性

Mongo 始终保证**单个文档**的写是原子的（要么全成功要么全失败），这覆盖了大量业务：把相关数据内嵌进同一文档，就天然免事务。

```javascript
// 内嵌文档的更新是原子整体
db.accounts.updateOne(
  { _id: 1 },
  { $inc: { "balance.cny": -100, "balance.usd": 0 } }
)
```

## 三、多文档事务（4.0+）

语法类似关系库：

```javascript
const session = db.getMongo().startSession();
session.startTransaction({
  readConcern: { level: "snapshot" },
  writeConcern: { w: "majority" }
});

try {
  const orders = session.getDatabase("shop").orders;
  const inventory = session.getDatabase("shop").inventory;

  orders.insertOne({ _id: 100, sku: "x", qty: 1 }, session);
  inventory.updateOne({ sku: "x" }, { $inc: { stock: -1 } }, session);

  session.commitTransaction();   // 全部成功才提交
} catch (e) {
  session.abortTransaction();    // 任一处失败回滚
}
```

### 关键限制

- **默认 60 秒超时**：事务持锁且占用 oplog，须**短小快**，避免长事务拖垮集群。
- **不支持某些操作**：如 `createCollection`、索引创建、部分聚合阶段不能进事务。
- **分片事务（4.2+）**：跨分片事务需协调者，开销更大，且要求所有相关分片在线。
- **快照旧数据清理受限**：事务运行中，旧版本文档不能被 `WT` 回收（影响存储与性能）。

## 四、分布式事务代价与替代

MongoDB 官方明确建议：**能不用事务就不用**。因为事务在分片/复制集上有显著开销。常见替代：

1. **内嵌建模**（首选）：把多文档关系转为单文档，免事务。
2. **两阶段提交模式**：应用层用状态机（pending/committed）模拟，配合补偿。
3. **最终一致性 + 幂等**：用 oplog/Change Stream 异步对账。
4. **可重试写（Retryable Writes）**：单文档写在网络故障后可安全重试，配合 `w:"majority"` 实现「恰好一次」语义，覆盖很多场景。

## 五、Change Streams（变更流）

基于 oplog 的实时变更订阅，常用于 ETL、缓存失效、跨系统同步：

```javascript
const cs = db.orders.watch([ { $match: { operationType: "insert" } } ]);
while (cs.hasNext()) {
  printjson(cs.next());   // 实时拿到插入事件
}
```

Change Streams 天然支持断点续传（resume token），是「MongoDB → 其他系统」解耦同步的利器。

## 六、与关系库一致性对比

| 维度 | MongoDB | 传统关系库（如 MySQL） |
| --- | --- | --- |
| 单文档 | 原子 | 单行原子 |
| 多文档事务 | 4.0+ 支持，有开销，官方建议少用 | 原生、成熟、优化数十年 |
| 隔离级别 | snapshot（快照） | RR / RC / SERIALIZABLE 可选 |
| 默认一致性 | 最终一致（从节点读） | 通常强一致 |
| 设计哲学 | 用建模规避事务 | 用事务保证约束 |

> 结论：**MongoDB 强在灵活与扩展，事务是「补丁」而非「主场」**。需要强事务、复杂 join、严格约束的场景，关系库更合适（见 10.对比）。
