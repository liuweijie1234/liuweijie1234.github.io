# MongoDB 性能优化与监控

MongoDB 性能问题的 90% 可归结为「索引不当 / 工作集超内存 / 查询写放大」。本文给出从慢查询定位到系统性调优的完整方法论，并对比它与关系库的性能差异。

## 一、性能黄金三问

1. **工作集（Working Set）是否进内存？** 常用数据与索引应 ≈ 可分配给 WT 的 RAM。超出 → 频繁磁盘 IO，性能雪崩。
2. **查询是否走索引（IXSCAN）？** `explain()` 看有无 COLLSCAN。
3. **写是否放大？** 大文档 + 高频更新 + 过多索引 = 写瓶颈。

## 二、慢查询定位

开启慢查询日志（Profiler）：

```javascript
// 记录超过 100ms 的操作
db.setProfilingLevel(1, 100)
// 0=关, 1=超阈值记录, 2=全记录

// 查慢操作
db.system.profile.find({ millis: { $gt: 100 } }).sort({ ts: -1 }).limit(5).pretty()

// 聚合最慢操作
db.system.profile.aggregate([
  { $group: { _id: "$op", total: { $sum: "$millis" }, cnt: { $sum: 1 } } },
  { $sort: { total: -1 } }
])
```

更推荐用**数据库分析器 + mongod 日志**（`slowOpThresholdMs`），结合监控平台。

## 三、索引优化（复用 第 4 章）

- 用 `explain("executionStats")` 确认 `IXSCAN`、`totalDocsExamined ≈ nReturned`。
- 用 `$indexStats` 找出零访问索引并清理（减写放大）。
- 复合索引遵循 ESR（等值-排序-范围）顺序。
- 构建**覆盖索引**避免回表。

## 四、查询与建模优化

| 技巧 | 说明 |
| --- | --- |
| 投影只取所需字段 | 减少网络与文档解析开销 |
| 游标分页替代深 skip | `find({_id:{$gt:lastId}}).limit(n)` |
| 避免大数组无限增长 | 拆引用，否则读放大 |
| 预聚合 / 物化视图 | 用定时任务算好结果直接读（见 2.计算模式） |
| `$lookup` 谨慎用 | 频繁跨集合 join 说明建模该内嵌 |
| 批量写 `bulkWrite` | 减少往返，`ordered:false` 可并行 |

## 五、内存与存储引擎（WiredTiger）

- WiredTiger 用**缓存（cache）** 存放热数据与索引，默认上限 `max(50% RAM - 1GB, 256MB)`。
- 监控 `cache used %`：持续 > 90% 表示工作集超内存，需加内存或减数据。
- 开启 **压缩**（snappy/zstd），省磁盘但增 CPU；SSD 强烈推荐。
- **journal（WAL）** 保证崩溃恢复，不可关。

```yaml
storage:
  wiredTiger:
    engineConfig:
      cacheSizeGB: 4            # 显式限定缓存（容器部署务必设，否则吃满宿主机）
    collectionConfig:
      blockCompressor: zstd
```

## 六、写入性能

- **批量远大于单条**：网络往返是主要开销。
- `writeConcern: w:1` 比 `majority` 写快很多（权衡持久性）。
- 有序批量（`ordered:true`）遇错即停；无序（`ordered:false`）更快但乱序。
- 自增 `_id` 作哈希分片键避免单调写入热点（见 第 6 章）。

## 七、监控体系

### 7.1 内置命令

```javascript
db.serverStatus()        // CPU/内存/连接/操作计数
db.stats()               // 库级统计
db.users.stats()         // 集合级（含 indexSizes）
db.currentOp()           // 当前正在跑的操作（找慢查询/锁等待）
db.killOp(opid)          // 杀掉异常长操作
```

### 7.2 关键指标

| 指标 | 健康线 | 含义 |
| --- | --- | --- |
| `wiredTiger.cache.used` | < 80% | 缓存压力 |
| `globalLock.currentQueue` | ≈ 0 | 锁等待队列 |
| `opcounters` | 稳定 | 各类操作速率 |
| `connections.current` | < `maxConns` | 连接数 |
| `repl.lag` | 秒级 | 主从延迟 |

### 7.3 外部监控

- **MongoDB Atlas / Ops Manager**：官方可视化监控与告警。
- **Prometheus + Grafana**：`mongodb_exporter` 采集指标。
- **mongostat / mongotop**：命令行实时吞吐与热点集合。

```bash
mongostat --host 127.0.0.1:27017  # 每秒操作、内存、连接
mongotop 10                        # 各集合读写耗时
```

## 八、与 MySQL 的性能比较（核心视角）

MongoDB 常被拿来和 MySQL 比性能，但两者定位不同：

| 场景 | MongoDB 更优 | MySQL 更优 |
| --- | --- | --- |
| 灵活半结构化数据 | ✅ 无需迁移 DDL | 改表成本高 |
| 高写入吞吐（水平扩展） | ✅ 分片并行写 | 单主写瓶颈 |
| 复杂关联/join | ❌ 需 $lookup | ✅ 原生 SQL join |
| 强事务/严格约束 | ❌ 事务有开销 | ✅ 成熟稳定 |
| 嵌套对象存取 | ✅ 一次 IO | 需多表 join |
| 报表/即席分析 | 一般（聚合语法） | ✅ 优化器成熟 |

> 结论：**没有「谁更快」，只有「谁更契合访问模式」**。Mongo 胜在扩展性与灵活建模，MySQL 胜在事务与关联成熟度。详见 [10.与关系型数据库对比](./10.与关系型数据库对比.md)。
