# MongoDB 使用场景、限制与选型

「什么场景用 MongoDB」是工程师必须回答的选型问题。本文结合 第 1~8 章 的原理，给出适用场景、硬限制与决策清单，帮助你在项目中正确落地。

## 一、最适合 MongoDB 的场景

### 1. 敏捷开发 / 快速迭代的业务模型
需求频繁变动、字段不确定（如电商商品属性、营销活动配置），用 Mongo 的灵活 schema 免去了反复 `ALTER TABLE`。

### 2. 半结构化 / 多变数据
日志、埋点、IoT 时序、内容管理（CMS）、用户画像标签——字段随来源变化，文档模型天然适配。

### 3. 海量数据 + 高写入吞吐
配合分片（第 6 章），写入可水平扩展，适合订单流水、消息、feed 流。

### 4. 对象嵌套 / 树形结构
组织架构、评论嵌套、商品规格——一次查询取完整对象，避免多表 join。

### 5. 地理空间 / 全文检索
原生 `2dsphere` 地理索引与 `text` 全文索引，适合 LBS、地图、站内搜索。

### 6. 缓存层 / 中间存储
高吞吐读写 + TTL 自动过期，可作为特定场景的缓存或临时存储。

## 二、典型行业案例

| 行业 | 用法 |
| --- | --- |
| 电商 | 商品目录（多规格属性）、购物车、用户行为 |
| 游戏 | 玩家档案、装备、排行榜 |
| 物联网 | 设备遥测、时序分桶存储 |
| 内容/媒体 | 文章、评论、标签、CMS |
| 金融（边缘） | 风控特征、流水（非核心账务） |
| SaaS | 租户配置、动态表单 |

## 三、Mongo 的硬限制与不适用场景

### 3.1 技术限制

| 限制 | 说明 |
| --- | --- |
| 单文档 ≤ 16 MB | 不能存超文档；超大需 GridFS 或拆引用 |
| 字段名长度 / 嵌套深度 | 嵌套过深影响性能与可读性 |
| 事务开销 | 多文档事务有成本，长事务受限，不适合高频强事务 |
| join 能力弱 | `$lookup` 不如 SQL join 成熟灵活 |
| 内存依赖 | 工作集超内存性能骤降，需预留 RAM |
| 跨分片事务复杂 | 需要所有分片在线、协调开销大 |

### 3.2 不适用场景（别硬上 Mongo）

- **核心账务 / 强事务系统**：银行转账、库存扣减强一致——关系库 + 事务更稳。
- **复杂多表关联分析**：BI 报表、即席 join 查询——关系库/数仓更优。
- **高度规范化、强约束数据**：如税务、合同，约束与一致性优先。
- **超小数据量**：单机 MySQL 即可，引入 Mongo 反而增加复杂度。

## 四、选型决策清单

问自己：

1. 数据模型是否频繁变化？（是 → 倾向 Mongo）
2. 是否需要水平写扩展？（是 → Mongo 分片）
3. 是否强依赖多文档 ACID 事务？（是 → 倾向关系库）
4. 是否大量复杂 join / 报表？（是 → 关系库/数仓）
5. 是否有嵌套/半结构化对象？（是 → Mongo 优势）
6. 团队是否有 Mongo 运维能力？（分片集群运维门槛不低）

> 多数互联网业务是**混合架构**：用 MongoDB 存灵活业务数据，用 MySQL/PostgreSQL 存核心交易与账务，用 Redis 做缓存——各取所长。

## 五、常见误区

| 误区 | 正解 |
| --- | --- |
| 「Mongo 不需要设计，随便存」 | 建模（内嵌 vs 引用）直接决定性能，必须设计 |
| 「用 Mongo 就别建索引」 | 查询照样要索引，否则全扫 |
| 「事务都有，随便多文档事务」 | 官方建议少用，用建模规避 |
| 「分片能解决一切扩展」 | 运维复杂，先垂直优化 |
| 「替换 MySQL 全部」 | 应是补充而非全盘替代 |
