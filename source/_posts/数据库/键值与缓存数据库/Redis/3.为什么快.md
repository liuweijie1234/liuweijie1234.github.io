# Redis 为什么快

> 「单线程」常被误读为 Redis 的短板，实则是它快的关键之一。本文从内存、单线程、IO 多路复用、数据结构四个维度拆解，并澄清 6.0 引入的 IO 多线程。

---

## 1. 纯内存操作（基础）

数据驻留内存，随机访问纳秒级，省去磁盘寻道。所有读写直接在内存完成，这是速度的物理基础。

---

## 2. 单线程命令执行（避免竞争）

核心：**网络 IO 之外的命令执行是单线程串行的**。

优势：

- **无锁开销**：不需要加锁/解锁、无死锁、无上下文切换；
- **原子性天然保证**：单条命令、Lua 脚本都是原子的；
- **实现简单、可预测**：无需处理并发数据结构。

> 常见误解：「单线程 = 性能差」。实际上 Redis 瓶颈通常是**内存带宽/网络 IO**，而非 CPU。单线程足以跑满十万级 QPS。

---

## 3. IO 多路复用（epoll / kqueue）

Redis 基于 **Reactor 模式**：单线程通过 `epoll`（Linux）/ `kqueue`（macOS）同时监听成千上万个连接，事件就绪才处理，避免「一连接一线程」的资源爆炸。

```
            ┌─────────────────────────────┐
  多客户端  │  epoll 监听 socket 事件      │
  ─────────►│  事件就绪 → 单线程依次处理   │
            │  (读命令 → 执行 → 写回)      │
            └─────────────────────────────┘
```

源码对应 `ae.c` 事件循环：文件事件（连接/读写）+ 时间事件（定时），单线程在二者间轮转。

> 正因为 IO 多路复用，单线程也能高并发处理海量连接。

---

## 4. 高效的数据结构

- **SDS**：O(1) 长度、预分配；
- **跳表**：范围查询高效；
- **渐进式 rehash**：字典扩容时**分步**迁移，不一次性卡顿；
- **ziplist/listpack**：小数据紧凑存储，省内存。

> **渐进式 rehash** 很关键：一次性 rehash 大字典会阻塞单线程，Redis 把迁移拆成每次增删改时搬一点，平滑无感。

---

## 5. 6.0+ IO 多线程（突破网络瓶颈）

命令执行仍单线程，但**网络读写（IO 线程）可多线程并行**，解决大流量下的网络收发瓶颈。

```ini
io-threads 4              # 开 4 个 IO 线程
io-threads-do-reads yes   # 读也走多线程（默认仅写）
```

> 何时开：QPS 很高、Value 大（网络吞吐成为瓶颈）时收益明显；普通场景单线程已足够，多线程反而增加复杂度。

---

## 6. 其他加速点

- **协议简单**：RESP 文本协议，解析快；
- **基于 VM 友好**：热数据常驻，较少 swap；
- **避免慢命令**：`KEYS`、大 `HGETALL`、`FLUSHALL` 会阻塞单线程，生产用 `SCAN`、管道（pipeline）、批处理。

---

## 7. 小结

Redis 快 = **纯内存（快） + 单线程（无锁无切换） + IO 多路复用（高并发连接） + 高效结构（省 CPU/内存）**。理解它，才能在缓存、锁、集群场景不踩性能坑。下一章 **持久化** 讲清「内存数据库如何不丢数据」。
