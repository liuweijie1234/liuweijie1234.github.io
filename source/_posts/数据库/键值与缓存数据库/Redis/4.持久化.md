# Redis 持久化

> Redis 是内存数据库，但也能落盘。本文讲清 RDB 与 AOF 两种机制、优劣势、混合持久化与选型，避免「重启数据全丢」的事故。

---

## 1. 为什么需要持久化

内存掉电即失。持久化让 Redis 重启后能恢复数据，也支撑主从同步的基线。

两种方式：**RDB（快照）** 与 **AOF（追加日志）**，可同时开启。

---

## 2. RDB（快照）

定时把某一时刻的**内存全量数据**二进制压缩写入 `.rdb` 文件。

### 触发方式

```bash
SAVE            # 主线程同步保存（阻塞，勿用）
BGSAVE          # 后台 fork 子进程保存（推荐）
```
配置自动触发：

```ini
save 900 1       # 900 秒内至少 1 次修改
save 300 10
save 60 10000
```

### 原理：fork + 写时复制（COW）

`BGSAVE` 时父进程 `fork` 出子进程，二者共享内存页；子进程负责写盘，**父进程继续服务**。只有被修改的页才真正复制，极大减少内存占用。

### 优缺点

| 优点 | 缺点 |
| --- | --- |
| 文件紧凑、恢复快 | 两次快照间宕机 → 丢失该段数据 |
| 适合备份/灾难恢复 | fork 大内存时有停顿（Copy-On-Write） |
| 对性能影响小 | 数据量越大 fork 越慢 |

> 默认文件名 `dump.rdb`，目录由 `dir` 指定。

---

## 3. AOF（追加文件）

记录**每一条写命令**到 `appendonly.aof`，重启时重放恢复。

### 配置

```ini
appendonly yes
appendfsync everysec     # 每秒刷盘（默认，兼顾安全与性能）
```

`appendfsync` 三种策略：

| 值 | 行为 | 安全性 |
| --- | --- | --- |
| `always` | 每条命令 fsync | 不丢，最慢 |
| `everysec` | 每秒 fsync | 最多丢 1 秒 |
| `no` | 交给 OS | 可能丢较多 |

### AOF 重写（Rewrite）

AOF 会无限增长（如 `INCR` 一万次）。重写**生成等价的最小命令集**，压缩体积：

```bash
BGREWRITEAOF
```

配置自动重写：

```ini
auto-aof-rewrite-percentage 100   # 体积翻倍触发
auto-aof-rewrite-min-size 64mb
```

原理同样是 fork 子进程重写，不影响主线程。

---

## 4. 混合持久化（推荐）

Redis 4.0+ 支持 **RDB-AOF 混合**：AOF 重写时，把当前数据以 **RDB 格式** 写入文件头，后续增量用 AOF 命令追加。

```ini
aof-use-rdb-preamble yes
```

优点：RDB 的快速恢复 + AOF 的更少丢失，二者兼得。

---

## 5. 选型与建议

| 场景 | 建议 |
| --- | --- |
| 纯缓存（可丢） | 关闭持久化，性能最高 |
| 可接受分钟级丢失 | 仅 RDB（`save` 策略） |
| 高可靠 | 开启 AOF + 混合持久化 |
| 容灾备份 | RDB 定时备份到对象存储 |

> 重启恢复优先级：AOF（若开）优先于 RDB。

---

## 6. 运维要点

- 监控 `rdb_bgsave_in_progress`、`aof_rewrite_in_progress`；
- 大内存实例 `BGSAVE` 的 fork 延迟（`latest_fork_usec`）需关注；
- 主从架构下，从库也可承担 `BGSAVE` 减轻主库压力。

---

## 7. 小结

RDB 省空间、恢复快但有丢失窗口；AOF 更可靠但文件大；**混合持久化**是现代默认推荐。下一章进入 Redis 最核心的工程话题——**缓存设计**（穿透/击穿/雪崩/一致性）。
