# Redis 缓存设计

> 引入缓存的 90% 工作量不在「怎么写」，而在「怎么不出事故」。本文系统拆解缓存与数据库的一致性、三大经典问题（穿透/击穿/雪崩）与最佳实践。

---

## 1. 缓存定位与读写模式

缓存是**数据库的前置加速层**。最常用 **Cache-Aside（旁路缓存）**：

### 读流程
```
1. 查缓存 → 命中返回
2. 未命中 → 查 DB
3. 写入缓存（设 TTL）→ 返回
```

### 写流程（推荐：先更新 DB，再删缓存）
```
1. 更新数据库
2. 删除缓存（下次读自动回填）
```
> 为什么「删缓存」而非「更新缓存」：避免并发写导致缓存与 DB 不一致，且懒加载更简单。

---

## 2. 缓存与数据库一致性

### 2.1 先删缓存再更新 DB（不推荐）
窗口内若有读请求，会回填**旧值**到缓存 → 长期不一致。

### 2.2 先更新 DB 再删缓存（推荐，Cache-Aside）
极端并发下仍可能不一致（删缓存失败 / 删后旧读回填），用补偿：

**延迟双删**：
```
1. 删缓存
2. 更新 DB
3. 休眠 500ms
4. 再删缓存     # 兜底清掉期间回填的旧值
```

**订阅 binlog 异步删**（生产级）：用 **Canal/Debezium** 监听 MySQL binlog，消息队列异步删/更新缓存，彻底解耦。

> 绝对一致很难：缓存本质牺牲强一致换性能。业务需评估能否接受「最终一致」。

---

## 3. 缓存穿透（查不存在的数据）

**现象**：大量请求 key 在 DB 也不存在 → 每次穿透到 DB，缓存形同虚设，DB 被打挂。

**解决方案**：

1. **缓存空值**：不存在的 key 也缓存 `null`，设较短 TTL，防重复穿透；
   ```bash
   SET user:999 "NULL" EX 60
   ```
2. **布隆过滤器（Bloom Filter）**：在缓存前加一层，判断 key 是否可能存在，不存在直接拒绝；
   > 优点：空间极小；缺点：有误判（说存在可能不存在，说不存在一定不存在）。
3. **参数校验**：非法 ID（负数、超长）在入口拦截。

---

## 4. 缓存击穿（热点 Key 失效）

**现象**：某个**热点 key** 突然过期，瞬时大量请求同时击穿到 DB。

**解决方案**：

1. **互斥锁（分布式锁）重建**：
   ```java
   if (cache miss) {
     if (tryLock(key)) {        // 只放一个线程去 DB 加载
       data = db.load();
       cache.set(key, data);
       unlock(key);
     } else { sleep 50ms; retry; }
   }
   ```
2. **逻辑过期**：Value 中存过期时间，不真实过期；发现过期才异步重建，期间返回旧值；
3. **热点 Key 不过期**（后台定时刷新）。

---

## 5. 缓存雪崩（大量 Key 同时失效 / Redis 宕机）

**现象**：大量 key 同一时刻失效，或 Redis 集群整体不可用 → DB 瞬时洪峰。

**解决方案**：

1. **TTL 加随机值**：`expire = base + random(0, 300)`，错开失效；
2. **多级缓存**：本地缓存（Caffeine/Guava） + Redis + DB，Redis 挂也有本地兜底；
3. **限流 + 熔断 + 降级**：Hystrix/Sentinel 保护 DB；
4. **Redis 高可用**：主从 + 哨兵 / Cluster，避免单点（见 第 7 章）；
5. **预热**：上线前批量加载热点数据。

---

## 6. 大 Key 与热 Key

| 问题 | 危害 | 解决 |
| --- | --- | --- |
| **大 Key**（如 10MB 的 Hash） | 删除/迁移阻塞、网络拥塞 | 拆分（按 field 分片）、分批删除 |
| **热 Key**（某 Key 瞬时超高访问） | 单节点 CPU 打满 | 本地缓存副本、Key 加随机后缀打散到多节点 |

---

## 7. 最佳实践清单

- 给所有缓存设 **TTL**（防止冷数据常驻）；
- 区分「缓存」与「存储」：缓存不背最终数据源职责；
- 批量用 **Pipeline / MGET**，减少 RTT；
- 监控命中率（`keyspace_hits / (hits+misses)`），过低说明缓存设计有问题；
- 写时谨慎选择「删 vs 更」，强一致场景走 binlog 同步。

---

## 8. 小结

缓存工程 = **一致性方案 + 三大问题防御 + 大/热 Key 治理**。下一章用 Redis 实现 **分布式锁与消息队列**——缓存之外的另一大主场。
