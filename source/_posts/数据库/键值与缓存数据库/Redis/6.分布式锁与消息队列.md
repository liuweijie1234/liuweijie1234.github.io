# Redis 分布式锁与消息队列

> 分布式系统里，Redis 常客串两个角色：**分布式锁**（协调互斥）与**消息队列**（异步解耦）。本文讲清正确姿势、常见坑（误删/锁丢失/Redlock 争议）与队列实现。

---

## 1. 分布式锁

### 1.1 错误示范

```bash
SETNX lock:order 1        # 加锁
... 业务 ...
DEL lock:order             # 释放
```
问题：① 无过期 → 宕机死锁；② 误删别人锁（业务超时，锁已过期被他人获取，自己 DEL 了别人的锁）。

### 1.2 正确姿势：SET NX EX（原子加锁+过期）

```bash
# 值用唯一标识（如 UUID/线程ID），保证只删自己的锁
SET lock:order $uuid NX EX 30
```
- `NX`：不存在才设（互斥）；
- `EX 30`：自动过期，防死锁。

### 1.3 安全释放：Lua 脚本（原子校验+删）

```lua
-- 仅当 value == 我的 uuid 才删
if redis.call("get", KEYS[1]) == ARGV[1]
then
  return redis.call("del", KEYS[1])
else
  return 0
end
```
> 必须用 Lua 保证「判断+删除」原子，否则高并发下仍有误删窗口。

### 1.4 锁续期（Watch Dog）

业务可能超过 `EX` 时长。方案：
- **Redisson 看门狗**：加锁后后台定时（默认 1/3 过期时间）续期，业务结束释放；
- 自己实现：后台线程定期 `PEXPIRE` 延长。

### 1.5 可重入锁

用 Hash 结构记录 `lock:order {holder: 重入次数}`，加锁时若持有者相同则计数 +1，释放时 -1，归零才删除。Redisson 已内置。

### 1.6 Redlock 算法与争议

**Redlock**：向 N 个独立 Redis 节点申请锁， majority（≥N/2+1）成功且总耗时 < 锁有效期才算获取，提升单点故障容忍。

```bash
# 伪流程：向 5 个节点各 SET NX EX，>=3 成功且时间窗口内 → 持锁
```

⚠️ **争议**：Martin Kleppmann 指出 Redlock 在「时钟跳跃 / GC 停顿 / 网络延迟」下仍可能不安全，建议用 **ZooKeeper/etcd（基于租约/ fencing token）** 做强一致锁；Redlock 适合「性能优先、偶尔重复执行可接受」的场景。

> 选型：强一致选 etcd/ZK；高吞吐、可重试业务选 Redis 锁（带唯一标识 + 续期 + Lua 释放）。

## 2. 消息队列

### 2.1 List 实现简单队列

```bash
LPUSH queue:task task1        # 生产
BRPOP queue:task 5            # 消费（阻塞）
```
- 缺点：无 ACK、无消费组、消息丢失（宕机且未处理）。
- 适用：轻量、可丢的任务。

### 2.2 ZSet 实现延迟队列

用 `score = 执行时间戳`，消费时取到期任务：

```bash
ZADD delay:queue <执行时间戳> task1
# 消费：取 score <= now 的最小任务
ZRANGEBYSCORE delay:queue 0 <now> LIMIT 0 1
ZREM delay:queue task1
```

### 2.3 Stream（官方推荐，5.0+）

支持消费组、ACK、重复消费控制，是 Redis 版「Kafka-lite」：

```bash
XADD mystream * field1 v1        # 生产
XGROUP CREATE mystream g1 $      # 建消费组
XREADGROUP GROUP g1 c1 COUNT 10 STREAMS mystream >
XACK mystream g1 <msg-id>        # 确认
```
> 相比 List/Pub-Sub，Stream 有持久化、消费组、Pending 列表，适合严肃队列场景。

### 2.4 发布订阅（Pub/Sub）

```bash
SUBSCRIBE channel1
PUBLISH channel1 "hello"
```
- 特点：实时广播，**不持久化**（离线丢消息）；适合通知、聊天室，不适合可靠队列。

## 3. 小结

分布式锁要点：**SET NX EX + 唯一标识 + Lua 释放 + 看门狗续期**；严肃场景评估 Redlock 局限。消息队列按可靠性选 List（轻量）/ ZSet（延迟）/ Stream（严肃）。下一章 **高可用与集群** 解决单点与服务扩展。
